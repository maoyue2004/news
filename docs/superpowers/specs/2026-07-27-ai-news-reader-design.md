# AI 信源罗盘 → 每日阅读器

设计文档 · 2026-07-27

## 背景

已有一个 Artifact（`https://claude.ai/code/artifact/24e0433d-3c33-4e84-8638-0c663708b9c9`，标题「AI 信源罗盘」），
内容是一份静态的 AI 信源清单：97 个信源，24 博客 / 24 播客 / 13 newsletter / 12 媒体 /
11 实验室 / 10 视频 / 3 社区，63 个英文源、34 个中文源。页面只有分类导航、语言筛选和搜索。

目标是把它从「信源清单」变成「每日阅读器」：

1. 每天的新内容列表，带中文摘要
2. 最近一个月的内容可以追溯
3. 信源可以编辑（新增 / 删除）
4. 已读打钩，优质内容标星

## 核心约束

**Artifact 页面无法自己联网抓取内容。** 发布后的页面受严格 CSP 限制，
对外部主机的 fetch / XHR / WebSocket 全部被拦截。本账号可声明的运行时能力只有
`downloads` 和 `mcp`；`mcp` 只能调用 claude.ai connector，当前仅有 Google Drive，
无法用于抓取 RSS。

因此内容必须在**发布时**就烘焙进页面。整个系统由此分成两半：

- **离线半边**（每天跑一次的 agent）：抓取 → 摘要 → 生成 HTML → 重新发布
- **在线半边**（页面自身）：展示 + 记录已读/标星，纯前端，不依赖网络

## 架构

### 仓库

私有 GitHub 仓库（云端定时 agent 需要同步代码和数据）。本地路径 `/Users/yuemao/workspace/news`。

```
news/
├── sources.json           # 97 个信源，唯一真相源
├── scripts/
│   ├── fetch.mjs          # 并发抓 RSS/Atom → 去重 → data/_pending.json
│   └── build.mjs          # data/*.json + 模板 → dist/index.html
├── templates/page.html    # 页面骨架（CSS + JS）
├── data/
│   ├── seen.json          # 已抓条目指纹，滚动保留 45 天
│   ├── status.json        # 每个源最近一次成功/失败抓取的时间与连续失败次数
│   └── YYYY-MM-DD.json    # 当天条目 + 中文摘要 + 抓取错误
├── dist/index.html        # 生成物，发布用
├── DAILY.md               # 云端 routine 每天执行的流程
└── docs/superpowers/specs/
```

### 每日流程

云端 scheduled agent（routine），**每天北京时间 08:00** 触发。选这个时间是因为
欧美源前一天的更新此时已全部进来，且在上班前。

1. `node scripts/fetch.mjs`
   读 `sources.json` 中 `enabled: true` 的源，并发抓 feed，与 `seen.json` 去重，
   输出 `data/_pending.json`：每条含源名、原标题、链接、发布时间、正文前 2000 字。
2. Claude 分批读 `_pending.json`，为每条写**中文标题 + 3-4 句摘要**，
   写入 `data/YYYY-MM-DD.json`。
3. `node scripts/build.mjs`
   生成 `dist/index.html`，把最近 30 天的数据以 `<script type="application/json">`
   内嵌进页面。
4. 用 Artifact 工具以**原有 URL** 重新发布，链接保持不变。
5. `git commit && git push`。

**抓取用脚本而不是让 agent 逐个 WebFetch**，理由：RSS 解析是确定性的、可重试、可测试；
60 个源并发约 30 秒，而 agent 逐个抓要十几分钟；且正文不进上下文，token 成本低一个量级。
Claude 在流程里只做它不可替代的事——写中文摘要。

### 失败处理

单个源抓取失败不中断整体流程，错误记入当天数据的 `errors` 数组，
页面底部显示「今天有 N 个源没抓到」。某个源连续 7 天失败时，
routine 在汇报中点名，由用户决定修 feed 还是删除。

## 抓取范围

| 类型 | 处理方式 |
|---|---|
| 博客 / newsletter / 实验室 / 媒体 / 社区 | 抓全文，生成完整中文摘要 |
| 播客 / 视频 | 只抓新一期的标题和官方简介，翻译成中文；**不获取 transcript** |
| 无可用 feed 的源 | `enabled: false`，保留在信源列表中但不抓取 |

播客和视频条目在页面上带 🎧 / ▶ 图标，摘要明确标注「基于官方简介，未收听」，
不让它冒充内容摘要。

预计 97 个源中有 10-20 个找不到可用 feed（主要是中文公众号，
以及原清单里几个指向平台搜索结果页而非独立站点的条目）。这些标为
`enabled: false`，在「信源管理」视图中单独列出并注明原因，
而不是硬编一个可能失效的地址。用户之后找到可用地址可随时启用。

## 摘要规格

每条内容生成：

- **中文标题**：意译，不逐字直译
- **摘要**：3-4 句，约 60-120 字，说清「这篇在讲什么、结论是什么」

目标是让用户据此判断要不要点开原文，而不是取代原文。

## 信源编辑

`sources.json` 是唯一真相源。用户通过对话增删改（「加一个 X」「把 Y 删了」），
Claude 修改文件并 commit，次日生效。

页面上的「信源管理」是**只读**视图：列出全部 97 个源、类型、语言、
启用状态、最近一次成功抓取的时间。

之所以不做页面内编辑：页面能改的只有 localStorage，而云端 agent 读的是仓库里的
`sources.json`，两者无法互通，会导致「页面上删掉的源第二天照样冒出来」。
单一真相源换取零冲突。

## 页面设计

### 布局

**左栏（sticky）**

- 30 天日历列表：每天显示日期 + 条数，有未读时打点
- 下方两个特殊视图：`★ 收藏`（跨全部日期聚合）、`信源管理`

**顶部**

- 统计：`今日 23 条 · 未读 18 · ★ 5`
- 筛选：`全部 / 未读 / 已标星`
- 搜索框：同时搜中文摘要、中文标题和英文原标题

**主区**

当天条目**按类型分组**（博客 / newsletter / 实验室 / 媒体 / 播客·视频），
组内按发布时间倒序。分组而非纯时间流，是因为扫描时心智更稳定，想跳过某一类很容易。

每条的形态：

```
☐ ☆  Interconnects · 博客 · EN            2h ago
      RL 环境里的报酬黑客问题
      原标题 Reward hacking in RL environments
      ▸ Nathan 拆解了三类常见的奖励函数漏洞…（点击展开）
```

摘要默认折叠为 2 行，点击展开。标题链接到原文。

### 已读 / 标星

存于浏览器 `localStorage`，key 为条目 URL 的哈希（稳定，不随重新发布变化）。
点击即时生效，不依赖 agent。

**已知局限**：localStorage 按浏览器存储，换设备、换浏览器或清缓存会丢失。
Artifact 页面没有服务端存储，这是平台硬约束。

缓解：页面提供「导出收藏」按钮（用 `downloads` capability 生成 JSON 文件）
和对应的「导入」入口。日常已读状态丢失影响有限，标星内容值得定期备份。

### 主题与响应式

沿用原页面的配色系统（`--ink` / `--paper` / `--accent` 等 CSS 变量）
和 Fraunces 标题字体，保持视觉延续性。同时支持
`prefers-color-scheme` 和 `:root[data-theme]`，760px 以下折叠为单栏。

## 数据保留与页面体积

- `data/` 保留 35 天，更早的删除（git 历史中仍可追溯）
- 页面内嵌最近 30 天
- 体积估算：约 40 条/天 × 约 450 字节/条 ≈ 18 KB/天，30 天约 540 KB，
  加页面骨架约 600 KB，gzip 后约 150 KB。可接受。

## 不做的事

- 不做页面内的信源编辑（见「信源编辑」一节的理由）
- 不获取播客/视频 transcript
- 不做跨设备的已读/标星同步（平台不支持）
- 不引入 RSSHub 等第三方中转服务（长期维护成本高于收益）
- 不做推荐、排序权重、个性化——列表按类型和时间排，保持可预测
