### 本次改动一：抓取重试从「补一轮」改成「补两轮」

昨天上线的「网络类失败补一轮」**没有救回东方星痕**——它今天是连续第 6 天记为失败，
再过一天就到「连续 ≥7 天点名停用」的线。今天手动查证：

```
https://ystyle.top            → 200（首页活着）
https://ystyle.top/atom.xml   → curl 三次：reset / reset / 200（240KB）
https://geofftools.cn         → 000（连接失败）
https://geofftools.cn/blog/atom.xml → 000
```

三次 curl 只隔几秒，也就是说昨天留的两个假设——「代理抖动窗口比 20 秒长」
和「加轮次」——**是后者**：不是某个时间窗口整体不通，是**每一次连接独立地有概率被
reset**，大 feed 传输时间长、命中概率更高。拉长间隔没用，加次数才有用。
所以 `fetchAllSources` 加了 `retryRounds`（默认 2 轮补抓，合计 3 次机会），
每轮只重试上一轮仍失败的源，成本随轮次迅速收敛（今天第一轮失败 10 个，
第二轮剩 3 个，第三轮只会碰这 3 个）。
补了一条测试模拟「前两次 reset、第三次才通」，就是东方星痕的形状。

对照组是樵夫的小站：首页和 feed 都是连接失败，重试多少轮都不会回来，
它是真死。**这两个源今天都是 6 次连续失败，明天会分道扬镳——
如果分不开，说明这条改动没用，那时才该考虑换判据（比如失败时探一下站点首页）。**

### 3. 顺手改掉的假问题：小众软件论坛「30 个查询挂 15 个」是限流，不是站点抽风

这条从创刊起天天出现在 REVIEW 的「抓取失败」里，每次都被记成「老问题，长期如此」，
十天没人查过。今天实测：

```
8 个查询、400ms 间隔  → 8 个全过
30 个查询、同样间隔    → 7 过 23 挂，全部 HTTP 429
```

是 **Discourse 的匿名搜索限流**，响应体是中文的「您执行此操作的次数过多」，
**没有 `Retry-After` 头**可依。诊断本身很便宜：
**失败数随批量大小走而不是随时间走**，这就是限流的指纹。

也就是说这个源每天有七成以上的查询是发出去就注定被拒的：白等 23×400ms、
白占 23 次出口请求，还把一条噪声天天写进错误列表，盖住真正该被看见的失败。

修法是给源加 `maxQueries`（appinn 设 8）按额度截断，**不做退避重试**——
限流窗口按分钟计，而这个源近 10 天收录 0，不值得为它给日更管线加几分钟等待。
轮转池每天切片不同，被截掉的词第二天还有机会轮到。
顺带修了一处会掩盖故障的分母：截断之后「整源失败」必须按**实际发出的条数**判，
否则「8 发 8 挂」会被算成「8/30 部分失败」混过去。两条都固化成了测试。

### 1. 顺手查出来的大洞：`SEARCH_QUERIES` 的轮转不是轮转

手册第 4 条让我「看 `SEARCH_QUERIES` 里有没有长期零产出的查询词」。
翻 `query-yield.json` 时先看到的是一个说不通的数字：**跑够 5 轮的只有 6 个核心词**，
而核心词根本不参与轮转。轮转池 254 条、每天 24 条，11 天就该走完一圈，
账本却记了 13 天。

按每个词在池子里的位置画出「跑过几轮」，形状立刻不对了：

```
位置 0 ────────────────────────────────────────────── 253
轮次 00000000000000000011111111112222222222222222222233332222…4444444…3333…0000000000000000000000000000
     └ 头部 18 个 0 ┘                    └ 中段最高 4 轮 ┘        └──── 尾部 61 个词全是 0 ────┘
```

一个中间高、两头零的平滑驼峰。**13 天 312 个查询槽，只碰到 254 个词里的 145 个，
尾部整整 61 个（24%）一次都没跑过**——包括 Spec Kit / OpenSpec / Superpowers /
DeepAgents / Muse Code / DSH / Headroom / CC Switch / Cowork，以及**全部** TOPICS
派生词（MCP 怎么用、Agent Skills 实践、CLAUDE.md 实践、Hooks 实践、Worktree 隔离实践…）。

成因是 `queriesForDate()` 的窗口起点：

```js
const start = ((days * rotating) % pool.length + pool.length) % pool.length;
```

`days` 是两万多的大数，而 `pool.length` **每改一次词表就变一次**——
取模的结果随之跳到一个毫不相干的位置。也就是说这不是「每天平移 24 格」的连续覆盖，
是「每次改词表就随机重开一次」，于是中段被反复采样、两头永远够不着。
我在这一轮里改了五次词表，就等于把轮转重掷了五次骰子。

危害有两层，第二层更隐蔽：**供给**上凭空少搜了四分之一的词；**账本**上
`query-yield` 永远攒不够轮次——手册第 4 条后半句「找出长期零产出的查询词换掉」，
只要这个 bug 在，就**永远执行不了**。上一轮体检写「等下周轮转池跑满一圈再动」，
而池子从来没跑满过一圈。

改法是让「什么时候轮到你」和池子长度脱钩：`cycle = ceil(池子 / 每日额度)`，
第 i 个词属于第 `i % cycle` 桶，当天跑第 `days % cycle` 桶。性质变成
**每个词每 cycle 天恰好跑一次**，中间插一个新词只让它后面的词各挪一个桶
（早一天或晚一天），不会把所有人重新洗一遍。
实测：池子 259 条、周期 11 天，每天发 28-30 个（额度 30），11 天覆盖 259/259，一个不漏。

**不变的**池子跑 14 天。这又是 LESSONS 里那句「测试测的是规则的意图，
不是规则在真实分布下的行为」。新加的两条测试改成断言演化过程：
一条锁「每个周期恰好一次」，一条**每两天往池子中间插一个词**，跑 20 天，
断言原有的 200 个词一个都没漏。
