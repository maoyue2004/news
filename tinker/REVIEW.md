### 本次最大的发现：FORUM_SHARE 从写下起就没在「文章够多」的日子生效过

当天分数最高的一条——V2EX「当 agent 说我做完了」，16 分，全场第一——
被规则判了「论坛/搜索源已达当日占比上限」，没进人工评审。
同时占满 60 席的是掘金上一批「Claude Code 平替方案有哪些」「Cursor 替代品有哪些」，
同一个 SEO 选题换五个标题反复发。**分数最高的进不来，农场文占八成**，
这个组合足够反常，按 LESSONS 里那条「分布过于整齐时先怀疑管道」查了 `triage()`，
挖出两个各自独立的实现问题：

**问题 1：论坛席位是余量，不是预留。**

```js
const takenArticles = byQuota(articles, cap);                       // 文章先按 cap 取满
const budget = Math.max(FORUM_FLOOR, Math.round((takenArticles.length * s) / (1 - s)));
const takenForums = byQuota(forums, Math.min(budget, cap - takenArticles.length));
```

`budget` 算出来是 40，但 `cap - takenArticles.length` 已经是 0，取 min 归零。
也就是说文章型源自己够 60 条的那天，论坛一席都拿不到，`budget` 白算。
更糟的是它断崖式跳变：59 条文章时论坛能拿 39 席，60 条时直接归零。
现在改成先按 `cap * forumShare` 预留席位、文章拿剩下的，再用**实际取到的文章数**
按原公式 s/(1-s) 把预留收紧——后半步保住原有意图：博客集体安静的那天，
论坛不该反过来变成名单主体（这一条原来的测试 202 已经在测，改完仍然通过）。

**问题 2：补位轮完全不看按源配额。**

`byQuota()` 第一轮守 `quota = 8`，第二轮把 overflow 往回填时不再读 `used`，
于是 `PER_SOURCE_QUOTA` 对高产源等于不存在。今天掘金一家吃下 45/60。
现在补位放宽到 `quota * QUOTA_RELAX`（=16）为止。

**代价说清楚**：这条会让名单在「只有一个源有货」的日子变短——今天就是
60 → 36。原来的测试 209 断言 25 条同源文章至少入围 20 条，现在只能进 16，
我把它改成了三个源，并新增一条测试专门锁「一个源最多 quota*QUOTA_RELAX 席」。
**改断言是有意的**：入围名单是评审预算，不是必须填满的额度，
36 条干净候选比 60 条里混 29 条农场文更好评。这一点和 LESSONS 里

### 今天最该记住的一件事：那些「失败的源」根本没失败

抓完照例有 7 个失败源，6 个是 `HTTP 503`，形状和前几天一样。按手册这就该往下走了——
但 SkyWT / 樵夫的小站 / 东方星痕已经**连续 5 天**记为失败，离「连续 ≥7 天点名停用」只剩两天，
所以顺手 curl 了一下，结果 **curl 全是 200**。

追下去发现 503 不是站点给的，是**本环境的出口代理**给的：

```
HTTP/2 503
x-deny-reason: resolve_failed
content-length: 48
"DNS resolution failed (transient resolver error)"
```

另一种是 `upstream connect error ... TLS_error: Connection reset by peer`。
**代理自己在响应体里写了 transient**，而 `get()` 只把 `res.status` 拼成 `HTTP 503` 抛出去，
上层根本分不清「站点死了」和「出口抖了一下」，一律计进 `consecutiveFailures`。

用 node 的 fetch 按 20 秒间隔连打三轮：SkyWT / 东方星痕 / 韩小韩 三轮全 200，
明明如月 / Watermelonabc / 浦明 立刻 200，只有樵夫的小站（geofftools.cn）三轮全挂。
**7 个「失败源」里 6 个是活的。**

代价不是少抓一天——今天回头拉这 6 个 feed，7-25 之后一条新文都没有，内容上零损失。
代价是**源的死活判断建在一个被污染的计数上**：再过两天就会按代理噪声去停用两个健康的博客，
而停用之后它们再也不会被抓，错误无法自我纠正。

**这也解释了 8-01 那批「同一时间戳一起挂掉」的源。** 上一轮 REVIEW 记的是
「像是同一家托管挂了」——不是托管，是那一轮出口 DNS 抖了，同一批请求一起中招，
所以时间戳才会一模一样。**分布过于整齐时先怀疑管道**，这条在 LESSONS 里已经写着了
（掘金 sort_type 那次），今天又对了一次，只是这回管道在我们这一侧。

### 3. 顺手改掉的假问题：小众软件论坛「30 个查询挂 15 个」是限流，不是站点抽风

这条从创刊起天天出现在 REVIEW 的「抓取失败」里，每次都被记成「老问题，长期如此」，
十天没人查过。今天实测：

```
8 个查询、400ms 间隔  → 8 个全过
30 个查询、同样间隔    → 7 过 23 挂，全部 HTTP 429
```

是 **Discourse 的匿名搜索限流**，响应体是中文的「您执行此操作的次数过多」，
**没有 `Retry-After` 头**可依。诊断本身很便宜：
**失败数随批量大小走而不是随时间走**，这就是限流的指纹。

也就是说这个源每天有七成以上的查询是发出去就注定被拒的：白等 23×400ms、
白占 23 次出口请求，还把一条噪声天天写进错误列表，盖住真正该被看见的失败。

修法是给源加 `maxQueries`（appinn 设 8）按额度截断，**不做退避重试**——
限流窗口按分钟计，而这个源近 10 天收录 0，不值得为它给日更管线加几分钟等待。
轮转池每天切片不同，被截掉的词第二天还有机会轮到。
顺带修了一处会掩盖故障的分母：截断之后「整源失败」必须按**实际发出的条数**判，
否则「8 发 8 挂」会被算成「8/30 部分失败」混过去。两条都固化成了测试。
