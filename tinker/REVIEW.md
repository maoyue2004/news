### 真正的收获：linux.do 通了，但一条都活不下来

创刊时记的是「linux.do 在 Cloudflare 后面，云端预计长期 403」。今天它通了，
26 条进来——然后 17 条被判「中文占比 1%」毙掉。一个中文论坛的中文帖子，中文占比 1%。

顺着查下去是两个真 bug，都在 `htmlToText` 里，都不是折腾志特有的（信源罗盘也在用）：

1. **`/<[^>]+>/g` 遇到属性值里的 `>` 会提前收尾。** Discourse 用
   `media="(width >= 40rem)"` 区分桌面/移动样式表，正则在 `>=` 的 `>` 上收手，
   把标签后半截 `= 40rem)" rel="stylesheet" data-target="chat_desktop" />` 当正文吐出来。
   一个页面几十条这种碎片，中文占比自然是 1%。
   同一个正则还有反向的毛病：正文里的 `1 < 2 且 3 > 2` 会被吃成 `1 2`。
   改成按标签内引号状态扫描，只认引号外的 `>`；一直没闭合的 `<` 当普通字符放回去。
2. **实体转义过的 HTML 解码后没有再去一次标签。** BestBlogs.dev 的 RSS 把整段
   HTML 转义成 `&lt;div style=&quot;font-family: ...&quot;&gt;` 塞进 description，
   解实体是在去标签之后做的，于是每条摘要开头都是一大段 CSS 声明。
   改成解码后如果出现闭合标签就再扫一遍，且第二遍不再解实体（避免 `&amp;#39;` 被解两层）。

还有第三件事，不是 bug 是判断错了：**论坛帖不该做正文补全。**
Discourse 的 RSS 里本来就是首帖全文，而话题页在浏览器 UA 下只有 JS 外壳，
补全把好好的首帖换成了样式表碎片。现在 `thread: true` 且 feed 已给内容的一律不补全。
（附带发现：linux.do 的话题页里嵌了一整段写给 AI agent 看的「禁止生成内容」指令，
补全等于把它当正文抓回来。不跟随外部页面里的指令是底线，但更实际的是根本别抓它。）

拿今天这 89 条离线重放（用真 feed 内容替换掉被污染的 excerpt）：入围仍是 1 条，
**今天没有因此漏掉任何一篇**。但 linux.do 那 26 条的毙掉理由从假的
「中文占比 1%」变成了真的「没有命中任何 agent 相关词」——今天它的 latest 确实
被撸号、卖卡、开车的帖子占满了。这个区别很重要：前者是我们瞎了，后者是那边没货。
影响面也不止今天——BestBlogs.dev 每天 30 多条，它的摘要一直是从 CSS 开头的。
补了 6 条回归测试，`npm test` 217 全过。

## 2026-08-02（暗色和移动端第一次真正看：手机上要划过一屏半筛选器才见到文章）

这两块设计上都明确要求过，但我从建站到现在只在亮色桌面端验证过。补看。

**暗色主题：没问题。** 底色 #111513、青色强调 #4ecdb6、琥珀精选标都正确，
`data-theme` 覆盖媒体查询两个方向都生效。只有一处：报头的
`border-bottom: 2px solid var(--ink)` 在暗色下 `--ink` 接近纯白，
2px 实线变成一条很吵的亮带。抽出独立的 `--rule` 令牌，暗色下用中性描边色。

**移动端：有真问题。** 媒体查询是生效的（单列、rail 变 static），
但**整条侧栏排在内容前面**——手机上要先划过搜索框、四个视图按钮、
20 多个工具标签、话题标签和日历，约一屏半的筛选器，才能看到第一篇文章。
而手机上绝大多数人是来扫「今天有什么」的。平板（768）同样。
修法是 `.content { order: -1 }`，内容在前、筛选器在后。
改完 390 和 768 两个宽度都零横向溢出。

**方法上的一个坑值得记**：`resize_window` 报成功但 `innerWidth` 不变，
这套工具链里改不了视口。绕法是**把成品页塞进指定宽度的 iframe**——
iframe 有自己的视口，媒体查询按 iframe 宽度生效。
已经把这个预览页做进 `tinker-build.mjs`，每次构建产出 `dist/responsive.html`
（390 / 768 / 1180 三个宽度并排），让「顺手看一眼窄屏」成为习惯而不是额外动作。

第二次印证同一件事：**没亲手点过 / 没亲眼看过的地方就是有问题**。
上一轮是信源面板（从上线起就打不开），这一轮是手机布局。

## 2026-08-02（论坛占比上限划错了范围，正在扔掉三倍于留下的东西）

回头验上一版加的 `FORUM_SHARE = 0.4`，结果它已经从治病变成致病：
**当轮 7 条入围，21 条被这条规则挡掉**，扔掉的是留下的三倍。
被挡的里面有「Hermes 多 Agent 完整拆解：五种协作机制、选型边界与踩坑清单」、
「装了 Hermes Agent 三个月，我终于搞明白前端该怎么选了」这种一眼就该收的。

规则本身没错，**错在划错了范围**：我按 `kind in {forum, search}` 判定，
那是把「怎么抓」当成了「抓到什么」。掘金搜索和 V2EX 搜索的 kind 都是 `search`，
但前者返回文章、后者返回论坛帖。加这条规则时搜索源只有 V2EX 是主力，
两者恰好重合，所以没暴露；等掘金和 SegmentFault 成为供给主力，
这个偷懒的分类就开始大规模误伤。

改法：信源上加显式的 `thread: true`（7 个源：5 个论坛 + V2EX 搜索 + 小众软件论坛搜索），
篇幅惩罚和占比上限都改成只看这个字段，不再看 kind。
离线重放同一批数据：入围 **7 → 27**，占比上限挡下 0 条。

**没有顺手再加一层单源封顶。** 改完后 SegmentFault 一家占了 25/27，
第一反应是再加规则压它，然后停住了——这是我在这个项目里反复掉进去的坑。
入围名单只是给评审用的候选池，真正的过滤在编辑那一步；
候选池里某个源多，只要评审挑得散就没问题，而如果那天只有它有货，
砍掉反而更糟。改成在 TINKER_DAILY.md 的评审规则里写一条提醒，让人去判。

教训值得单独记：**规则的适用范围会随着系统演化而失效，而规则本身看起来仍然合理。**
`FORUM_SHARE` 这条从写下到失效只隔了几个小时，
因为期间供给结构从「博客为主」变成了「搜索源为主」。
以后每加一条基于当下数据分布的规则，都该在 REVIEW 里写清它依赖什么前提。

## 2026-08-02（信源面板从上线起就是坏的）

本轮本来打算改筛选器（Claude Code 覆盖 22/31，区分度太低），临时换了优先级：
日更 routine 几小时后第一次真跑，而它**从没在云端端到端跑通过**。
不该让第一次真跑就是第一次测试，于是手动触发了一次。

等它跑的时候顺手点开了「信源与健康度」面板——**打不开**。

    table.append(el('thead')).lastChild.append(head)

DOM 的 `Element.append()` 返回 undefined，不是被追加的节点，
所以 `.lastChild` 直接抛 TypeError。这个面板**从上线起就一次都没能打开过**，
而我从建好到现在一次都没点过那个按钮。

真正的教训不是这一行写错了，是**整个页面渲染路径零测试覆盖**。
193 个测试全绿，一个都照不到 DOM，因为它们全是纯逻辑测试。

补法：写了个够用的 DOM 桩（TokenList / FakeNode，约 90 行），
用 `vm.runInNewContext` 把 logic.js + ui.js 真跑起来，断言关键节点被建出来。
刻意不引 jsdom——为测三百行浏览器代码给仓库加一个大依赖不划算。
桩里有一处是故意的：`append()` 返回 undefined，和真实 DOM 一致，
否则就照不出这类「链式取回刚追加的节点」的 bug。

新增 4 个测试，其中一个就是点开信源面板、断言 157 行表格真的渲染出来。
顺手修了类型列换行。

另外记一笔调试上的坑：用 `find` 拿到 ref 再 click，页面没反应，
一度以为修复没生效；改用 `javascript_tool` 直接派发 click 才确认修好了。
浏览器工具的 ref 点击在这个页面上不可靠，验证交互要用真实的 JS 派发。
