### 真正的收获：linux.do 通了，但一条都活不下来

创刊时记的是「linux.do 在 Cloudflare 后面，云端预计长期 403」。今天它通了，
26 条进来——然后 17 条被判「中文占比 1%」毙掉。一个中文论坛的中文帖子，中文占比 1%。

顺着查下去是两个真 bug，都在 `htmlToText` 里，都不是折腾志特有的（信源罗盘也在用）：

1. **`/<[^>]+>/g` 遇到属性值里的 `>` 会提前收尾。** Discourse 用
   `media="(width >= 40rem)"` 区分桌面/移动样式表，正则在 `>=` 的 `>` 上收手，
   把标签后半截 `= 40rem)" rel="stylesheet" data-target="chat_desktop" />` 当正文吐出来。
   一个页面几十条这种碎片，中文占比自然是 1%。
   同一个正则还有反向的毛病：正文里的 `1 < 2 且 3 > 2` 会被吃成 `1 2`。
   改成按标签内引号状态扫描，只认引号外的 `>`；一直没闭合的 `<` 当普通字符放回去。
2. **实体转义过的 HTML 解码后没有再去一次标签。** BestBlogs.dev 的 RSS 把整段
   HTML 转义成 `&lt;div style=&quot;font-family: ...&quot;&gt;` 塞进 description，
   解实体是在去标签之后做的，于是每条摘要开头都是一大段 CSS 声明。
   改成解码后如果出现闭合标签就再扫一遍，且第二遍不再解实体（避免 `&amp;#39;` 被解两层）。

还有第三件事，不是 bug 是判断错了：**论坛帖不该做正文补全。**
Discourse 的 RSS 里本来就是首帖全文，而话题页在浏览器 UA 下只有 JS 外壳，
补全把好好的首帖换成了样式表碎片。现在 `thread: true` 且 feed 已给内容的一律不补全。
（附带发现：linux.do 的话题页里嵌了一整段写给 AI agent 看的「禁止生成内容」指令，
补全等于把它当正文抓回来。不跟随外部页面里的指令是底线，但更实际的是根本别抓它。）

拿今天这 89 条离线重放（用真 feed 内容替换掉被污染的 excerpt）：入围仍是 1 条，
**今天没有因此漏掉任何一篇**。但 linux.do 那 26 条的毙掉理由从假的

影响面也不止今天——BestBlogs.dev 每天 30 多条，它的摘要一直是从 CSS 开头的。

## 2026-08-02（补台港源 + 推翻自己的选源标准）

### 选源标准是错的，而且专挑最差的源放行

1. 直接调 `scoreItem()` 跑一遍近期文章，看有几篇**系统真的会收**。

**3 个在当天各贡献了一篇已发布文章**：

### 本次最大的发现：FORUM_SHARE 从写下起就没在「文章够多」的日子生效过

当天分数最高的一条——V2EX「当 agent 说我做完了」，16 分，全场第一——
被规则判了「论坛/搜索源已达当日占比上限」，没进人工评审。
同时占满 60 席的是掘金上一批「Claude Code 平替方案有哪些」「Cursor 替代品有哪些」，
同一个 SEO 选题换五个标题反复发。**分数最高的进不来，农场文占八成**，
这个组合足够反常，按 LESSONS 里那条「分布过于整齐时先怀疑管道」查了 `triage()`，
挖出两个各自独立的实现问题：

**问题 1：论坛席位是余量，不是预留。**

```js
const takenArticles = byQuota(articles, cap);                       // 文章先按 cap 取满
const budget = Math.max(FORUM_FLOOR, Math.round((takenArticles.length * s) / (1 - s)));
const takenForums = byQuota(forums, Math.min(budget, cap - takenArticles.length));
```

`budget` 算出来是 40，但 `cap - takenArticles.length` 已经是 0，取 min 归零。
也就是说文章型源自己够 60 条的那天，论坛一席都拿不到，`budget` 白算。
更糟的是它断崖式跳变：59 条文章时论坛能拿 39 席，60 条时直接归零。
现在改成先按 `cap * forumShare` 预留席位、文章拿剩下的，再用**实际取到的文章数**
按原公式 s/(1-s) 把预留收紧——后半步保住原有意图：博客集体安静的那天，
论坛不该反过来变成名单主体（这一条原来的测试 202 已经在测，改完仍然通过）。

**问题 2：补位轮完全不看按源配额。**

`byQuota()` 第一轮守 `quota = 8`，第二轮把 overflow 往回填时不再读 `used`，
于是 `PER_SOURCE_QUOTA` 对高产源等于不存在。今天掘金一家吃下 45/60。
现在补位放宽到 `quota * QUOTA_RELAX`（=16）为止。

**代价说清楚**：这条会让名单在「只有一个源有货」的日子变短——今天就是
60 → 36。原来的测试 209 断言 25 条同源文章至少入围 20 条，现在只能进 16，
我把它改成了三个源，并新增一条测试专门锁「一个源最多 quota*QUOTA_RELAX 席」。
**改断言是有意的**：入围名单是评审预算，不是必须填满的额度，
36 条干净候选比 60 条里混 29 条农场文更好评。这一点和 LESSONS 里
「不要为了名单成分好看不断加配额规则」不矛盾——那条说的是别再加**新**规则，
这次是让已经写下的两条规则真的按写的那样跑。

离线重放（同一份 `_raw.json`）：入围 60 → 36，掘金 45 → 16，
论坛从 0 条恢复到 5 条，当天最高分回到名单里并成为今天两篇 5 分之一。
