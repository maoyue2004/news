**这份要每次开工前完整读一遍。** 它不是流水账（那是 `REVIEW.md`），
只放已经被数据验证过、且下次还会用得上的结论：踩过的坑、走不通的死路、
以及那些「看起来合理但实测是错的」判断。

改动规则：新结论要有数据依据；推翻旧结论要写清是什么数据推翻的，

## 词表与匹配

**别名的唯一标准：它单独出现时是否只可能指这个产品。** 和语言、长度都无关。
三次踩坑，一次比一次隐蔽：

| 别名 | 误命中 | 为什么规则拦不住 |
|---|---|---|
| `dia` / `amp` | ASCII diagram、example | 子串匹配，加词边界可解 |
| `&amp;` → Amp | feed 正文里的 HTML 实体 | 前后都不是拉丁字母，词边界无效，要单独排除 `&` 前缀 |
| `心流` → iFlow | 「核**心流**程」 | 中文没有词边界，两个字的别名基本都会误伤 |
| `operator` → ChatGPT Desktop | Kubernetes Operator、C++ 重载、`operator: 'eq'` | 它本身就是独立单词，任何边界规则都拦不住 |

同类嫌疑仍在表里靠打分权重压着：`comet` `crush` `goose` `continue` `jules`。
下次误判就删。

**别名还有第二种错法：不是误命中，是认错人。** 上面那张表里的每一条都是
「一个词顺带撞上了别的东西」，命中里有对有错，靠打分权重还能压一压。
2026-08-10 发现的是另一种：`workbuddy` 从创刊那天起写在 `cowork`（Claude Cowork）的
`aka` 里，而 **WorkBuddy 是腾讯 CodeBuddy 团队的桌面办公 agent**（workbuddy.cn，
文档挂在 codebuddy.cn/docs/workbuddy 下），两家公司的两个产品。
这种别名**每一次命中都是错的，一次都不对**，权重压不了，只能拆成独立词条。
症状是它一直很安静：误命中会在 `preReasons` 里留下明显不搭的组合，
而认错人看起来完全正常——「标题命中：cowork」出现在一篇讲 WorkBuddy 的稿子上，
一眼扫过去毫无破绽。**加别名时除了问「它会不会撞上别的词」，还要问
「它本身是不是别人的名字」。**

**「认错人」里最难的一种：一个产品的名字被另一个产品的名字整个包住，拆词条不够。**
2026-08-11 量到第二例：`TRAE Work`（字节的桌面办公 agent）15 条命中、14 条在标题，
全部被判成 `Trae`（它家的 IDE）——`trae` 全部 26 条标题命中里这批占了一多半，
页面上点「Trae」筛选器过半是另一个产品。和 `workbuddy` / `cowork` 是同一类错，
但那次两个名字不共一个字母，**拆开就完了；这次 `TRAE Work` 里带着 `Trae`**，
加了 `trae-work` 词条之后裸 `trae` 照样每篇都命中一次。
所以词条支持一个可选的 `not`：匹配前先把被排除的短语从文本里**抹成等长空格**再跑。
抹成等长而不是删掉——删掉会把两侧字符黏起来，破坏 `makeMatcher` 的词边界判断。
好处是它只影响被标注的那个词条：「TRAE Work vs Trae」这种同时提到两者的标题两个都命中。
**判据的第三问：除了「它会不会撞上别的词」「它本身是不是别人的名字」，
再加一句「有没有别人的名字把它整个包住」。**
（配套一条：`UNQUERYABLE` 从此不只装「太泛的名字」，也装「不泛但脏」的——
`trae-work` 名字很独特，但它的中文语料几乎全是投稿稿，主动搜等于每天往入围名单里
灌一批注定被毙的东西。**词条要加**（不然标签是错的），**查询词不要**。）

**别名的第三种错法：为了躲误伤，限定词贴得太紧，于是漏掉正常语序。**
前两种错法（误命中、认错人）都是「收多了」，这一种是「收少了」，而且**完全不报警**。
2026-08-11 一次量出三处：`worktree` 19 条只认出 4 条、`spec-driven` 14 条只认出 6 条、
`agent skills` 只写了复数、`ai coding` 整个漏在 `SOFT_TERMS` 外面。
以 worktree 为例，别名写的是 `agent worktree` / `worktree 并行`——要求限定词**紧挨着**词，
而真实标题是「多个 AI Agent 同时改一个项目，我用 git worktree 让它们互不打架」，
限定词在句子里，不在词旁边。
**查法：拿 `_raw.json` 对每个话题算「文本里出现 / 被别名认出」两个数，比值低的就是这一类。**
放宽的安全边界仍然是那条老规矩，只是要用数据而不是想象来定：
`git worktree` 命中 13 条**逐条看完全部是 agent 语境**（连唯一一条从纯 git 讲起的
「Git Worktree 实战：从多分支并行，到 AI Agent 隔离」也是），才敢收；
裸 `worktree` 那 6 条差额里有 tmux 编排和纯分支管理，仍然不收。
三字母缩写（`SDD`）也是一样：10 条命中逐条查过，没有一条是别的意思，才加。

**别名的第四种错法：判断本身没错，但词的所有权会随时间转移。**
前三种（误命中、认错人、限定词贴太紧）都是写下来那一刻就错了；这一种是**当初对、后来过期**。
2026-08-17 一次量到两处：`harness` 的注释写着「test harness / wire harness 都是常用词，
绝对不收裸词」，`skill` 写着「soft skill / skill tree 都是常用词」——
在 1350 条中文语料里，这两类反例**各 0 条**，而漏掉的是
裸 `harness` 52 条（全部 agent 语境，55 条标题里有它）、裸英文 `skill(s)` 153 条（18 条在标题）。
中文技术语料在这一年里把这两个词整个让给了 agent。
**判据：凡是「因为会撞上别的意思所以只收限定词」的别名，都要定期拿新语料复量一次
「那个别的意思还在不在」**；量法和放宽 `git worktree` 那次一样——先算「出现 / 被认出」，
再逐条看差额，反例为零才动。放宽时把「出现第一次误伤就退回去」写进注释，免得下次重查。
（附带一条边界：这次只放宽了英文写法。中文的「技能」照旧不收——招聘帖里
「技能要求」「技能包括」满地都是，而中文没有词边界。）

**反向词表也要过正向词表那三问，尤其是「它是不是某个常用词的一段」。**
`ANTI_MARKERS` 从创刊起就没按这个标准审过。2026-08-17 查出 `低价` 是**「低价值」的一段**：
18 次命中里 7 次是 `低价值`（「不允许发明低价值工作」）和 `低价团`（旅游新闻），
误杀的那篇是「AI 写了一个月代码，人类只提交 13 次」——作者把仓库拉下来数了 841 次提交、
把人类那 13 次逐条点开。而真正的黑产帖**每一条都同时命中 `中转`**，删掉 `低价` 一条不漏。
**但删之前一定要量「唯一命中数」和「删掉后会翻成入围的条目」**，光看「这个词看起来太泛」会改错：
同一轮里 `广告`（48 次命中，抽样 14 条只有 1 条真是广告）看起来更该删，
实测删掉翻进来 4 条、其中 3 条是垃圾（招聘 JD、跨境专线试用、PH 热榜），
和 08-03 量 `免费额度` 得到的是同一个结论——**看起来该删，实测它挡住的比误伤的多。**

**别名的第五种错法：一条为了防误伤而立的规矩，会顺手把一个真产品挡在词表外。**
前四种（误命中、认错人、限定词贴太紧、词的所有权转移）说的都是某一条别名写错了；
这一种是**一条正确的规矩被推得太远**。`vocab.mjs` 从创刊起就写着
「Claude / Gemini / Qwen / Kimi 那几个裸词是模型名，所以**不**给它们的 CLI 条目
加裸别名」——这句话本身对，2026-08-24 发现它被当成了「所以裸 Claude 整个不能收」，
于是词表里有 `claude-code`、`claude-desktop`、`cowork` 三个产品，
**唯独没有 claude.ai 那个聊天产品本身**。后果是一整类作者结构性隐形：
iT 邦幫忙那批繁中系列通篇只写「Claude」不写产品全名，工具命中恒为 0。
376 条语料里裸 `claude`（排除四个同名产品和模型名）标题命中 26 条、全文 39 条，
**逐条看完没有一条是 Claude Monet 这类同名的人**；代价不在误命中而在噪声
（「为啥现在 claude 订阅都是自己充值」这类账号帖）。离线重放的账是入围 34 → 37，
2 条要的、2 条噪声。**判据：「不给 X 的 CLI 加裸别名」和「X 本身不是产品」是两句话，
别让前一句替后一句作决定；重读老注释时，先分清它否掉的是别名还是词条。**

**词边界不只被中文破坏，也被标点破坏。** 同一轮里现成的测试当场抓到：
`CLAUDE.md` 里 `claude` 后面跟的是 `.`，不是拉丁字母，`makeMatcher` 认为这是词尾，
于是「我给项目写了 CLAUDE.md」同时挂上了工具 `claude` 和话题 `claude-md`。
和「心流 → 核心流程」是同一句话的两半：那次是中文没有词边界，这次是
**分隔符本身就是合法边界**。凡是加英文裸词条，先问一句「它后面接 `.` `-` `_` `/`
的时候，构成的是不是另一个东西」。

**而这一问要四个分隔符**逐个**问完，问了一个不算问过。** 2026-08-27 被自己这句话打脸：
上面那次只补了 `.`（`claude.md` / `claude.local.md`），`_` 和 `/` 一个没补，
于是裸 `claude` 在三种写法上继续认错人整整三天——
`CLAUDE_CODE_MAX_RETRIES` 这类**环境变量**、`~/.claude/`（settings.json / skills /
sessions / projects / ide）这个**配置目录**、`claude_desktop_config.json`。
三者的所有者分别是 Claude Code、Claude Code、Claude Desktop，一个都不是 claude.ai。
症状和「认错人」那一族一样安静：犀利豆那篇讲重试的全文 6 处 claude **全是 Claude Code**，
标签上却挂着聊天产品，一眼扫过去毫无破绽。
615 条语料量下来 64 → 60，掉的 4 条全对、0 误伤。
**配套一条边界**：**不能**顺手加裸的 `claude/`——同一份语料里
`把 Google Veo 接进 Claude/Cursor`、`一次配置，Claude/Cursor/Codex 全通用`
是**拿斜杠当顿号的列举**，那里的裸 claude 说的确实是这个聊天产品。
也就是说四个分隔符里，`.` `-` `_` 后面接字母时几乎一定是别人的名字，
而 `/` 两可——它既是路径分隔符也是顿号，只能连着后面那个词一起遮。

**别名里的空格是字面的：`多 agent` 和 `多agent` 是两个匹配器，写一个等于只写了一半。**
2026-08-31 加 `multi-agent` 话题时当场被测试抓到：别名只写了带空格的 `多 agent`，
而真实标题是「多**Agent**协作的5个工程坑」——中间没有空格。
`makeMatcher` 对纯 ASCII 的 needle 做的是逐字符 `indexOf` + 词边界检查，
**不做任何空白归一化**，所以两种写法必须都写。
危险的一半在 `not` 遮罩上：遮罩只写了 `更多 agent`，那么「更多Agent能力」照样命中，
**而这一半不会有测试替你抓——正向别名写漏了会立刻表现成「这个词一条都认不出来」，
反向遮罩写漏了只表现成名单里多了一条噪声。**
这是「每加一个新字形的源，回头把所有中文正则查一遍」的第四个变体：
前三次换的是简繁、半角/全角括号、同一个东西的方言词，**这次换的是空格有没有**。

**同一个词的两种字形，会各自撞上不同的常用词——简体量过，不代表繁体安全。**
这是「心流 → 核心流程」那一族的第六例，也是第一次出现在**补字形**这个动作里。
2026-08-31 给 `ANTI_MARKERS` 补繁体写法时，`中轉` 的 2 条唯一命中**全部**是
「繁**中轉**譯」（「繁中轉譯來源卡片與 placeId 去重」「Google Maps Grounding 繁中轉譯」）。
简体那半从创刊起没出过事，因为简中语料里没人把「简体中文」缩写成「简中」再接一个动词；
而繁中圈「繁中 / 簡中」是日常缩写。
**判据：补字形不是机械对译，每一个新写法都要重新过一遍那三问。**
同一轮里被数据挡回来的还有四个，走的是另一条理由——`免費額度`（5 条唯一命中，
误伤 2 篇 5 分，而「免费额度用完」正是那两篇的题眼）、`課程`（9 → 误伤 1 篇 4 分）、
`優惠`（3 → 1 篇）、`解鎖`（2 → 1 篇）：
**这几个词的精度在两边语料里本来就不一样**，简体那半量的是 V2EX / linux.do 的卖号帖，
繁体这半量的是 iT 邦铁人赛和 vocus 的个人写作。和 `低价` 那条同族，
只是那条说的是删一个已有的词，这条说的是别加一个看起来对称的词。

**而正向词表的字形洞比反向词表贵一个数量级，因为它错的方向相反。**
2026-08-31 量到：`EXPERIENCE_MARKERS` 从创刊起是照简中语料写的，
而繁中源（iT 邦八个铁人赛系列 + vocus + 台港博客）已占入围名单四分之一。
1396 条里逐对量：記錄 55、小時 47、教訓 28、實測 27、體驗 18、從零 18、一個月 16、
總結 12、怎麼用 12、替換 11、一週 11、天後 10、為什麼我 9、試用 8、實踐 7……全部认不出来。
**反向词漏一个字形是少毙一条噪声，正向词漏一个字形是给一整个语种的作者系统性降权**，
而且**会连带压住条件式规则**：`SERIAL_TITLE` 只在正文经验词 ≥4 时把罚分减半，
繁中连载的经验词有一多半认不出来，于是「Day N」那条罚分对繁中作者恒定按最重的一档走。
离线重放：越过入围线 11 条（全是繁中）、跌破 0 条、已发布条目受损 0 条。
08-16 早就发现过「`SELF_PROMO` 整张表在繁体语料上从来没有命中过一次」并补全了那一张，
**但没有人回头看这一张**——「回头把所有中文正则查一遍」里的「所有」是字面意思。

**查字形缺口不要凭想象列简繁对，把语料里那个位置的字按频次拉出来看。**
同一轮补 `FIRST_PERSON_ACTION` 时用的方法：把 1396 条标题里所有「我(们)+X」的
下一个字统计一遍（`我的` 21、`我用` 18、`我把` 7、`我讓` 3、其余各 1-2 条），
**唯一够得上数的繁体缺口就是 `讓` 一个**。凭想象列会同时漏掉真缺口、加进一堆零命中的字。

**一个候选源「够格数低」可能量的是词表，不是这个源。** 承上：iT 邦 9045
（22 篇的 IT 診斷 Agent 開發實錄）按旧词表逐篇抓正文打分 **1/22 过线**，
看起来是标准的不够格；加上裸 `claude` 之后 **4/20**，Day 15 拿 14 分。
准入判据调用的是系统自己的 `scoreItem()`（这一条没错，见下面「选源判据要用系统
自己的评分器」），但**评分器的视力由词表决定**，词表有洞时它会把整整一类源
判成不够格，而且和真的不够格长得一模一样。
**次序：先修词表，再回头把最近几轮「够格数低」的候选重新量一遍**——
和「词表大改之后重扫一次 harvest 是有价值的」是同一条账，只是那条说的是索引，
这条说的是逐个候选。

**「显示叫什么」和「见到这几个字母算不算命中」是两件事，别让 `name` 一个字段兼任。**
词条默认拿 `name` 当第一个匹配器，绝大多数时候没问题；但有一类产品的名字**本身就是常用词**，
而它又必须以那个名字显示在页面上。2026-08-24 量到第一例：`amp` 在 1173 条里命中 3 条，
两条是工具枚举里的 Amp，第三条是少数派那篇音频串流工具的「前级余量（**Pre-amp**）控制器」——
`-` 不是拉丁字母，是合法边界，`makeMatcher` 拦不住。
**代价更贵的一半在选源那一端**：同一天扫台港友链，`eddielv.com`（街头艺人 / 吉他效果器博客）
因为「MXR micro amp(M133)」「Xotic BB-preamp」被 `scoreItem()` 判成够格候选。
**裸词一旦进词表，污染的不只是当天的名单，还有「谁算 agent 博客」这个判断。**
改法不是 `not` 遮罩——那解决的是「别人的名字把我整个包住」，遮的是一个**具体短语**；
这里是「我的名字本身就不唯一」，pre-amp / op-amp / micro amp / 安培列不完。
所以词条支持 `bareName: false`：只从 `aka` 派生匹配器，`name` 只管显示。
同一轮里 `comet` `goose` `continue` `dia` 各 0 条、`crush` `jules` 各 1 条且全对，
**按「没量到就不动」全部留着**——这份嫌疑名单要逐个量，不能整批处理。

**量别名的账要用系统自己的匹配器，不能用手写正则。** 承上，同一次测量里
先用 `/\bamp\b/` 扫出 10 条，换成 `matchVocab` 只剩 3 条——差的 7 条全是 `&amp;`，
而 `makeMatcher` 的 `&` 前缀排除本来就把它们挡住了。
用正则量会把**已经修好的坑重新算成账**，然后照着这份假账去改一条好规则。
形状和「选源判据要用系统自己的评分器」是同一条，只是那条说的是评分，这条说的是匹配。

**这一族的第三例：犯规的可以是诊断工具本身，而它的产出长得像「你漏掉的好东西」。**
前两例（评分器、匹配器）说的都是「量一件事要用系统自己的那把尺」；
2026-08-29 发现 `tinker-retriage` 自己就没在用那把尺——它直接 `triage(items)`，
**不传 `publishedTitles`**，于是离线重放给出的名单和管线真正会产出的名单不是同一份。
症状比前两例危险得多：当天名单里凭空多出一条 9 分的 atbug《Docker Sandboxes 的
隔离例外》，读起来完全像「改了规则之后腾出席位补进来的好东西」，
**而它 08-21 就已经从 SegmentFault 收过、还是当天的 5 分精选**，
管线里被「严格同题」那道闸挡得好好的。差一点就照着这份名单把它再发一次。
**判据：凡是拿离线工具和管线对账，先确认这个工具吃的参数和管线一样；
口径不一致时，它报出来的差异有一部分是它自己造的，而这部分和真发现长得一模一样。**
（同族的下一句：这次的连带损失是 08-21 那条已发布条目的 `tools` 里没有
`docker-sandboxes`——当时词表没这个词条。**词表有洞时受损的不只是当天的匹配，
还有已经出过刊的那些条目的标签，而那些条目不会有第二次打标签的机会。**）

**这一族的第六例是第一次「在写诊断工具的当场」犯，而且救回来只花了一分钟。**
前五例（评分器、匹配器、诊断工具、取样口径、根本没有单位）全是事后才发现量错了。
2026-08-31 给「跑够 5 轮仍零入围的查询词」那行输出加池子过滤时，
第一版拿 `SEARCH_QUERIES` 当池子，跑出来 5 条**全部**判成「已退役」——
而 `Kilo Code 体验` 明明就印在当天的查询列表里。
成因是 `SEARCH_QUERIES` 只是手写长尾词那一半（73 条），
真正的池子是 `rotatingQueries()`（手写 + 词表派生，275 条）。
**一个名字听起来像「全部查询」的常量，可能只是其中一半**；
而这类错的症状是「过滤器把该留的全滤掉了」，看起来和「本来就没有」一模一样。
救回来靠的是一个很便宜的动作：**改完立刻拿真实账本跑一遍，看输出合不合常识**——
不是跑测试（测试会拿构造数据通过），是拿今天这份真数据看数字对不对得上。

**而一个词退役之后，它在账本里的计数会永远冻在退役那一刻，看起来仍像个待办。**
同一轮查出来的：`augment` 08-24 进了 `UNQUERYABLE`，此后 `Augment Code 踩坑 / 体验`
再也没跑过，但「跑够 5 轮仍零入围」那行照旧天天把它们印出来——
账本上的数字（14 轮 / 11 条 / 0 入围）和 LESSONS 里 08-24 记的**一字不差**，
正是「它根本没再动过」的指纹。这行输出的用途是「下一轮该换掉哪个词」，
而已退役的词**没有手术对象**。
**判据：凡是「累计型」账本喂给一份待办清单，都要先按当前还生效的集合过滤一遍；
退役条目单独列、不要删（想把它放回去时还要看当初的账），但绝不能混在待办里。**
形状和「落选理由写错了会把手术做在错的地方」是同一条，只是那条错在理由的措辞，
这条错在清单的成员资格。

**「显示叫什么」「算不算命中」「算不算分」是三件事，而第三件是 2026-09-03 才分出来的。**
前两件 08-24 因为 `amp` 分开了（`bareName: false`）。第三件逼出它的是 `rag`：
词表里有 `agent-memory`（记忆）却没有检索这一半，罗西那篇通篇拆两套 RAG 管线的稿子
（HardwareRag 纯关键词 vs Memory 的 cache → FTS5 → vector）**一个话题词都挂不上**。
洞是真的，但按普通话题加进去之后拿当天 487 条离线重放：
**越过入围线的 3 条全是噪声**（一条「[远程兼职] 8 年全栈…寻 AI Agent 方向」的求职帖、
一条阿里云沙龙全回顾、一条 RL 笔记），而该救的那条本来就在名单里（9 → 10 分，名次没动）。
**净收益 0 条，代价 3 个评审席位。**
形状和 `低价` / `免費額度` / `广告` 那一族一样——看起来该加，实测翻进来的是垃圾——
只是那三条说的是反向词该不该删，这条说的是正向词该不该给分。
两个结论都对且不冲突：**标签要加**（标签错了就永远错了，已发布条目没有第二次打标签的机会），
**分不要给**（RAG 自己是一个独立的大领域，「提到 RAG」离「这篇在讲 agent 折腾」还差得远）。
所以词条支持 `score: false`：`matchVocab` 一个都不滤（页面标签照挂），
`scoreItem` 走 `scoringHits()` 把它滤掉。
**和 UNQUERYABLE 是同一句话的第三段：词条要、查询词不要、分也不要。**
判据：**这个词命中的语料里「在讲 agent 折腾」的比例低到不足以当证据**；
下结论前先拿 `tinker-retriage` 重放一遍，看越线的那几条分别是什么——
光看「这个词命中的都对」只量到了标签那一侧，量不到它把谁抬过了线。

**「客户端渲染」记进账本时等于「今天没试」，不是「试过了不行」。**
2026-09-06 的 boyouquan（博友圈，771 个简中个人博客）：09-04 搜到它、当天记的是
「`/blogs` 是客户端渲染，静态 HTML 里一个站外域名都没有，留给周更」，09-05 原样又挂了一遍待办。
今天照 vocus 那条「拿不到搜索接口时，先翻一遍页面自己在调什么」把 `main.<hash>.js`
拉下来 grep `/api/`，第一屏就是 `/api/blog-intimacies/all-source-blogs`——
**一次请求给全部 771 条 `{blogName, domainName}`**，公开可调、无需签名。
和 vocus 那次是同一条通道的第二例，只是那次挖的是 `__NEXT_DATA__` 里的 SWR fallback key，
这次挖的是 webpack bundle 里的路由常量；**顺手撞上的 `/api/blogs` 每页只给 10 条**，
正是最容易让人下「这站不给列表」结论的那个入口。
判据：账本上写「客户端渲染 / 拿不到」的条目，要能答出「翻过它的 bundle 没有」；
答不出就还没查过，而它在待办里的样子和查过了一模一样。
（配套：它列的是**裸域名**，`parseSiteList` 靠正则找 `https?://`，读它出 0 条——
09-03「schema 不只指字段名，也指字段值的格式」的第三例。）

**工具和话题是两个维度。** `TOOLS` 是产品（能安装、能打开），
`TOPICS` 是概念与实践（MCP、CLAUDE.md、Vibe Coding、规格驱动开发）。
打分时等价，页面上必须分开——混在一个叫「按工具」的筛选器里是分类错误。

**查询词从词表自动派生，不要手写。** 手写会和词表脱节：
加了工具忘了加查询，这个工具就永远搜不到。

**但「换掉零产出的查询词」这条指令的粒度是查询，能执行的开关粒度是工具，
两者不能直接换算。** 2026-08-24：`通义灵码 实践` 跑够 5 轮 0 入围，照字面读该换掉它，
而同一个工具的 `通义灵码 踩坑`（08-04）和 `通义灵码 体验`（08-23）各出过 1 条——
按那条查询把整个 `lingma` 塞进 UNQUERYABLE 就砍错了。同一轮里 `Augment Code`
三条派生查询合计 **14 轮、11 条原始条目、0 入围**，`lastShortlist` 全是 null，
这才是能下结论的形状。**判据：这个工具派生的所有查询都跑够轮次，且合计零入围。**

**但「自动派生」不等于「真的被搜过」——按天平移的窗口，起点里不能带着池子长度。**
2026-08-17 查出轮转池从来没有真的轮转过：起点是 `(days * rotating) % pool.length`，
`days` 是两万多的大数，**池子每加一个词（也就是每次改词表）取模结果就跳到不相干的位置**，
于是「每天平移 24 格」变成「每改一次词表就随机重开一次」。
13 天 312 个查询槽只碰到 254 个词里的 145 个，**尾部 61 个（24%）一次都没跑过**，
其中包括全部 TOPICS 派生词。症状是按词表位置画出来的轮次是一个
**中间 4 轮、两头 0 轮的平滑驼峰**——又一次「分布过于整齐时先怀疑管道」。
改法是让「什么时候轮到你」和池子长度脱钩：`cycle = ceil(池子 / 每日额度)`，
第 i 个词属于第 `i % cycle` 桶，当天跑第 `days % cycle` 桶；
性质是每个词每 cycle 天恰好跑一次，中间插词只让后面的人各挪一个桶。
**两条推论**：(1) 这个 bug 同时废掉了 `query-yield.json`——账本永远攒不够轮次，
「换掉长期零产出的查询词」这条手册指令在修好之前根本执行不了，
**发现某个账本长期攒不够数据时，先怀疑写账本的那条路径而不是数据太少**；
(2) 原有的覆盖测试是通过的，因为它拿一个**不变的**池子跑 14 天——
**测演化中的行为要在测试里让输入本身变**（现在那条测试每两天往池子中间插一个词）。

## 信源

**博客不供货，搜索源供货。** 2026-08-02 实测：新增 51 个博客源
→ 23 条原始条目 → **0 条入围**；同一天 6 条入围全部来自搜索源。
中文个人博客写 agent 实践的池子是真的薄，不是挖得不够。
**别再把「加博客数量」当提高供给的手段**，力气花在查询词和新搜索平台上。

**「抓取失败」先分清是站点失败还是出口失败。** 2026-08-06：当天 7 个失败源
全是 `HTTP 503`，查下来 **6 个其实是活的**——503 来自本环境的出口代理，
响应体只有 48 字节，带 `x-deny-reason: resolve_failed`，正文写着
"DNS resolution failed (transient resolver error)"，**代理自己说了这是 transient**；
另一种是上游 TLS 被 reset。而 `get()` 只把 `res.status` 拼成 `HTTP 503` 抛出去，
上层分不清「站点死了」和「出口抖了一下」，一律计进 `consecutiveFailures`。
危险的不是少抓一天（那 6 个当天本来也没新文），是**源的死活判断建在被污染的计数上**：
SkyWT / 东方星痕已经连续 5 天记为失败，再过两天就会被按噪声停用，
而停用之后它们再也不会被抓，错误无法自我纠正。
现在抓取失败会重试一轮（`fetchAllSources()`，网络类失败才重试，404/403 不重试），
两轮都没拿到才记 failure。
**推论：一批源在同一时间戳一起挂掉，几乎一定是管道问题而不是托管商问题**——
8-01 那批「像是同一家托管挂了」的源，其实就是那一轮出口 DNS 抖了。

**搜索引擎发现不了博客，但发现得了「博客的名录」。** 这是对下面那条的补充，不是推翻。
2026-08-06 第七次验证「搜个人博客只出 SEO 平台页」之后换了个搜法：
不搜「XX 踩坑 博客」，改搜索引本身（`OPML` / `订阅列表` / `博客榜` / `feeds list`），
返回的立刻全是索引仓库。第五个索引 lotosbin/opml-list（1328 条 feed）就是这么找到的，
待接的 qianguyihao/blog-list（605 站，明确「不接受自荐」）也是。
**扩源缺的一直不是博客，是名录；按名录搜就有，按博客搜就没有。**

**找新博客只走社区索引，别走搜索引擎。** 三次同样的结果，别再试第四次：
搜索引擎返回的是 SEO 平台页和文档镜像站（opencodecn / learnopencode / claudecn 这类），
个人博客根本排不上去。2026-08-03 同一轮里做过直接对照——
4 组 WebSearch 探到 4 个候选站，逐个查完**一个都不够格**；
同一轮 `tinker-harvest.mjs` 扫 2986 个 feed，命中 19 个，人工过滤后并入 3 个。
搜索引擎的正确用途是**查证某个具体站点**（抽一篇看是不是转述文档），不是发现站点。

**harvest 会静默跑很久，不要按「多久没出字」判断它死没死。**
2986 个 feed 实测约 35 分钟，且进度全缓冲到结束时一次性吐出，
中途 `wc -c` 输出文件一直是 0 字节。踩过一次：以为它挂了，先按「本轮没并入新源」
收了尾，结果它带着 19 个命中正常退出。

**「这个源零命中」之前先量它的采样窗口有多宽。** 2026-08-11 查清死源时，
NodeSeek 是全库唯一一个「21 天 20 条、命中 agent 词表 0 条、入围 0、收录 0」的高量源，
看起来是标准的该停用对象。查下去发现 **它的 `rss.xml` 只给最新 20 条，而这 20 条跨度
21 分钟**——交易区和日常区发帖太快，一天抓一次等于每天只看 1440 分钟里的 21 分钟，
而且看到的永远是那一刻交易区在干什么。21 天 20 条这个数字本身就是「每天采到一次」的结果。
它的 channel 里明明白白列着 `tech` / `dev` 分类，只是我们从来没采到过。
（找过分类入口：`/categories/tech`、`rss.nodeseek.com/?category=tech` 等六种写法，
本环境下不是 403 就是被忽略，没有可用的窄入口。）
**推论：判一个源「不写这个主题」之前，先看它 20 条覆盖多少时间。
覆盖几个月 = 真的不写；覆盖几十分钟 = 你只是没看见。**

**同一个病，iThome 有药：窄窗口的解法是接子 feed，不是想办法把全站 feed 撑大。**
2026-08-13 量到第二例：`ithelp.ithome.com.tw/rss/articles` 固定 20 条，
铁人赛赛季里这 20 条只跨 **327 分钟**——每天只看得见清晨五个多小时发的东西。
分页参数（`?page=2` / `?limit=100`）**全部被忽略**，返回和第一页一字不差，
所以扩窗口这条路是死的；但 `rss/series/<id>` 通，一个系列 30 条全给。
和 NodeSeek 的区别就在这里：那边找遍六种写法没有可用的窄入口，这边有。
**先花五分钟试窄入口，再决定是接受采样还是放弃这个源。**

**窄入口的第二种形态：平台内的作者 feed；而漏掉它的代价由这个源有多好来决定。**
前两例（NodeSeek 21 分钟、iThome 327 分钟）都是**产量高但收录低**的源，
所以「看不见另外那些小时」听起来像损失了一批噪声；2026-09-02 量到的第三例正相反：
`博客园首页` 20 条只跨 **12.8 小时**，而它是创刊以来**收录量第二高**的源
（`rossiXYZ` 一人 9 篇含两篇 5 分，`znlgis` 3 篇全 5 分，`grey-wolf` 3 篇）。
也就是说这些人每天有一半的产出结构上进不来，**而它和「今天他们没发文」长得一模一样**。
窄入口是现成的：`www.cnblogs.com/<user>/rss`。
和「已收录作者是不是还在别处写」那条通道要分清——那条问的是**站外**
（作者自己的域名），这条问的是**同一个平台里更窄的那个入口**，原料同样免费送上门。
接的时候仍按严标准过 `evaluate()`：rossiXYZ 16/20、grey-wolf 6/20、
borui-coding-diary 4/13 三个接了，`znlgis` 2/20 卡在门槛线上、span 只有 14 天，
不接、留待复量（**卡线的候选宁可等一轮**，接进来的代价是每天几个必然被毙的席位），
七牛云那种官方号照旧只在源准入这一层整类不接。

**而「量窗口」本身不该靠人记得去量——三次的症状完全一样，三次都是有人想起来才发现。**
NodeSeek / iThome / 博客园首页 表现出来的都是「这个源没什么货、不写这个主题」，
和真的没货一个样。2026-09-02 照 08-30「一条每天靠记性重新量一遍的规矩不会收敛」
和 09-01 把 `readableCorpus()` 做进抓取尾部的同一条账，把它交给机器：
`lib/tinker/corpus.mjs` 的 `samplingWindows()`，每轮抓取固定点名窄窗口的源。
**判据里那条「条数够多才算」是必需的**——不加的话每天会把上百个安静的博客源全点名
（月更博客一轮就 1-2 条新文，跨度当然小，那不是 feed 被截断）；
现用 `n ≥ 15 且 span < 24 小时`。它量的是 seen 去重之后**本轮新拿到的**条目，
也就是「我们今天看见了多长时间」，不是「这个 feed 一共装得下多长时间」——
前者才是「今天漏了多少」要问的那个量。

**扩源的第三条通道：赛事 / 活动的报名表。** 前两条是社区名录（已榨干）
和已收录博客的友链页。2026-08-13 走通第三条：iThome 铁人赛的报名列表
`/2026ironman/signup/list?group=<组>` 按组列出全部参赛系列，
2026 年有 `claude-ai` / `chatgpt-and-codex` / `vibe-coding` / `ai-engineering`
等七个 AI 相关组，每个系列一条独立 feed。
和名录、友链问的问题都不同：名录问「谁被收进榜单」，友链问「写博客的人认识谁」，
报名表问的是**「谁正在为期 30 天地写同一件事」**——供给密度天然高，
而且报名时就按主题分好了组。
30 个系列 191 篇实测：够格的 2 个系列（5/13 和 2/5），一次并入两个源。
**两条配套的坑**：(1) 不能用 harvest 的 `evaluate()` 判准入——它带一条
「近 20 篇跨度 ≥14 天否则像媒体」的闸，而赛制就是日更 30 天，
所有参赛系列一律不合格；判据换成「近 20 篇里几篇过 `scoreItem()` 的入围线」。
(2) 这条通道有季节性（每年 8-9 月），系列停更后按常规留存标准自然沉底即可。

**列表页通道走通之后，第一件事是确认它有没有分页。** 2026-08-13 接铁人赛报名表时
按 `signup/list?group=<组>` 抓，每组返回 10 个系列，就当成「这个组一共 10 个」；
2026-08-17 翻第 2、3 页，四个 AI 组又多出 **28 个系列、120 篇**（第一页那 40 个系列是 387 篇）。
**第一页的产量不是这条通道的产量**，而漏掉的那批不会以任何形式报警。
（2026-08-22 又踩了这条的一个变体：`signup/list` **不带浏览器 UA 时一律 403**，
而 403 的响应体只有一千字节、解析出来是「这一页没有系列」，

LESSONS 早就写着「否则每次扩源都会重新提名」，踩的仍是这一脚——
因为「记下来」和「记到机器会读的地方」是两件事。

**「写完 REVIEW 顺手落 denylist」不是一条能靠记性执行的规矩——它已经被漏掉三次。**
2026-08-05 第三次：昨天 harvest 否掉的 6 个站今天原样又被提名，7 个命中里占了 7 个，
**新源 0**。而昨天写 REVIEW 时，我就在同一份文档里重申了「写在 REVIEW 里不算数」这条。
**否决和落盘必须是同一个动作**：翻 harvest 命中列表时，否掉一个就立刻写进
`denylist.json`，不要等写复盘时补。

**但 harvest 的边际产出不只跟索引走，也跟词表走。** 2026-08-17 第五次全量扫
（3337 个候选，同样六个索引）命中 4 个，并入 1 个——不是索引变了，是
`dsh` / `pi` / `cordis` / `harness` 这些词条 8 月才进表，同一批 feed 因此重新够格。
**词表大改之后重扫一次是有价值的，扫之前不必先说服自己「肯定是零」。**

**harvest 的边际产出：19 → 12 → 7 → 0。** 同样四个索引（timqian / blogcn /
top-rss / awesome-rss，2986 个 feed）连扫四次，第四次的 7 个命中**全部**是
第三次的落选者。这四个索引可以认为已经榨干；落盘 denylist 之后若下一轮命中 0，
就是硬证据——**别再跑同样的 harvest，去找第五个索引或换发现渠道。**

**而记到机器会读的地方还不够，得记成机器真的匹配得上的形状。**
2026-08-04 api.xgo.ing 第三次被提名：denylist 按完整 feed URL 精确匹配，
而它是个 RSS 网关，每个用户一条 `/rss/user/<hash>`，同一个站能生成无限条
互不相同的 URL。现在否决按**域名**生效；例外是 wechat2rss 这种一个域名下
挂几百个互不相干公众号的聚合网关，用 `scope: "feed"` 标出来单独放行。
**加任何黑名单前先问：被否的那个东西，下次会以同一个字符串出现吗？**

**「部分查询失败」长期稳定在某个比例，先怀疑限流，别当成站点抽风。**
小众软件论坛搜索「30 个查询挂 15 个」从创刊起天天写进 REVIEW 的抓取失败里，
每次都被记成「老问题，长期如此」——2026-08-11 实测下来是 **Discourse 的匿名搜索限流**：
按 400ms 间隔连发 30 个，第 8 个前后开始一律 `HTTP 429`（响应体是中文的
「您执行此操作的次数过多」，**没有 Retry-After 头**可依），当轮 23 个全废。
诊断很便宜：8 个一轮全过、30 个一轮挂 23 个，**失败数随批量大小走而不是随时间走**，
这就是限流的指纹。修法是给源加 `maxQueries`（appinn 设 8）按额度截断，
不是退避重试——限流窗口按分钟计，而这个源近 10 天收录数是 0，
不值得为它给日更管线加几分钟等待。
**顺带一条通用的**：截断之后「整源失败」的分母必须换成**实际发出的条数**，
否则 8 发 8 挂会被算成「8/30 部分失败」混过去。

**平台搜索必须显式按时间排序，默认排序会安静地废掉整批查询词。**
掘金原来用 `sort_type=0`（综合），返回的是历史高热文章：2026-08-03 实测
「Claude Code 踩坑」20 条结果里 **21 天窗口内 0 条**，最新一条是 6-19；
换成 `sort_type=1`（最新）后同一个词 20 条里 18 条在窗口内，最新就是当天。
症状极具迷惑性：当轮 30 个查询里 23 个零产出，而零产出的**全部**是词表派生词、
6 个核心词全部有货。看起来像「长尾词没人写」，实际是核心词热度够高、
连几个月前的老文章里也混得进新的，把排序问题伪装成了选词问题。
**分布过于整齐（恰好沿着某条分类线切开）时，先怀疑管道而不是内容。**
V2EX 用 `sort=created`、Discourse 用 `after:`，加新搜索源时第一件事就是确认排序参数。

## 筛选规则

**「限定词贴得太紧，于是漏掉正常语序」这种错，反向规则上也会犯，而且更安静。**
词表那一节记的是正向别名（`worktree` 只认紧挨着的限定词，漏掉「我用 git worktree 让它们
互不打架」）。2026-08-24 在 `isJobPost` 上量到同一个形状：那一支写的是
`招[\s\S]{0,4}?(…工程师…)`，而 Ruby China 的「[深圳] AI 智能硬件 + App 海外产品，
**招 Ruby on Rails 工程师**」中间隔着 15 个字符，于是它带着工具词拿 6 分进了入围名单。
**这条判据从来不是按语义写的，是按「岗位词紧挨着招」写的，而中文招聘帖的正常语序是
「招 <一串技术栈> <岗位>」。** 放宽到 24 个字符，1173 条标题里多命中 4 条、
**4 条全是招聘帖、0 误伤**。不敢开更大是因为 JOB 是硬毙，代价不对称。
差别在于：正向别名贴太紧是**少收**，会在「这个源够格数低」里留下痕迹；
反向规则贴太紧是**多收**，只会表现成名单里多了一条噪声，没人会去查它为什么没被拦住。

**`MIN_CJK_RATIO` 量的是 CJK 字符占比，它分不出中文和日文。**
2026-08-24 台港扩源时探到 `soulminingrig.com`，`evaluate()` 判 2/20 够格，
标题是「自宅用エージェントにkimakiでOpenCode無料枠」——**汉字够多的日文标题能过这道闸**。
这次是在门口挡住的（人工扫了一眼标题），但如果哪天接进来一个日文源，
它每天都会正常打分、正常入围，而这份刊物是中文的。
**加任何非简中来源之前，先确认它是中文站还是「汉字多的别的语言」。**

**规则的适用范围会随系统演化而失效，而规则本身看起来仍然合理。**
`FORUM_SHARE`（论坛占比封顶）从写下到失效只隔了几小时——
期间供给结构从「博客为主」变成「搜索源为主」，
而我按 `kind in {forum, search}` 判定，把「怎么抓」当成了「抓到什么」。
掘金搜索和 V2EX 搜索的 kind 都是 `search`，但前者返回文章、后者返回论坛帖。
后果是当轮 7 条入围、**21 条被这条规则挡掉**。
现在按信源上显式的 `thread: true` 判定。
**以后每加一条基于当下数据分布的规则，都要写清它依赖什么前提。**

**但发现「这条规则量的是怎么发」之后，别急着把罚分调小——先造语料量一遍。**
2026-08-13 是这个形状的第四例，也是**第一例「按老剧本改会改错」**。
`SERIAL_TITLE`（连载章节体标题 -4 分）在 iT 邦幫忙撞上铁人赛：
8-9 月赛季里那个平台上**所有**连载都必须叫 `Day N`，包括真折腾，
所以这条规则在这个平台上量的确实是「怎么发」。前三例（`FORUM_SHARE`、
V2EX 首帖篇幅、thin 席位）的结论都是「别按它扣分」，照抄就该减罚分。
**照抄会错。** 把 2026 铁人赛三个 AI 组共 30 个系列、191 篇正文拉下来重放：
罚 4 分够格 3 篇，罚 1 分够格 18 篇，多出来的 15 篇**逐条看完全部是教学连载**
（「認識 ChatGPT 與 Codex：AI 開發新搭檔」「什麼是Vibe Coding？」
「打造AI開發環境：Cursor / VS Code + AI插件最佳設定」）。
也就是说在这个平台上「Day N」和教程内容**确实**强相关，原判据只是不完备。
真正能分开两者的是**正文经验词密度**：那 15 篇是 1-3 个，
被误杀的那篇实录（「我的 AI 沒有資料庫：全 Markdown 架構」）是 4 个。
改法是**条件式罚分**——正文经验词 ≥4 时罚 2，否则照旧罚 4；
同一份 191 篇样本重放，够格数仍是 3，误杀那篇 5 → 7 进了名单。
**通用判据：放宽一条规则之前，造一份「这条规则的目标语料」（不是当天那 20 条）
去量各个档位的产出，再决定放宽哪个维度。凭直觉调数字会在正确的诊断上做错的手术。**
（2026-08-17 用 68 个系列 507 篇的**完整正文**复量了一次，结论不变：
阈值放宽到 ≥3 多进 5 篇、≥2 多进 9 篇，**全部是教学连载**。造这份语料时注意
RSS 描述只有 92 字符，用它量「正文经验词密度」等于量了个寂寞，必须逐篇抓页面
并用 `tinker-fetch` 同一个 `extractArticleText`。）

**规则层结构性看不见的一类作者：写结论、不写产品名。** 2026-08-17 复量铁人赛 9177
《一個人的 AI 團隊：Claude Code 當組長》，10 篇 **0 篇够格**、最高 3 分，
而标题是「中文亂碼是三種不同的病，先分流再治」「它回話了，不代表它做完了」
「能力會漂移，所以要有一張煞車燈」——人读起来明显好过分数。
病因不是 `SERIAL_TITLE`（罚分归零后最高的一篇也才压线 6 分），
是**工具名一次都没出现在标题上**，全靠正文命中拿 1-2 分，而标题命中值 6 分。
不要为这类作者放宽标题命中的权重——那会把一整片泛 AI 内容放进来。
**该记住的是结论本身：这类源即使收进来，它每天也只会落选**，
所以判「不收」的理由要写成「规则看不见它」，而不是「它分数低」。

**论坛帖的「篇幅」必须量首帖，量整页等于把导航和回复算成作者写的东西。**
`relevance.mjs` 的「论坛短帖 <600 字符扣 3 分」写得没错，但它在 V2EX 上
**从来没有量到过正确的字符串**。2026-08-09 实测三条入围帖：「codex 20260808 重置了」
首帖 0 字符、「所以买 codex pro 是没有意义的吗」0 字符、「Codex for oss…求支招」17 字符
（V2EX 首帖为空时页面里连 `topic_content` 这个 div 都不生成），
而它们的 excerpt 分别是 711 / 1305 / 793——页面固定 chrome 就三百多字符，
回复区再垫几百，任何一个纯标题帖都能凑过 600，还能从别人的回复里白捡
「正文经验词 3 个」的加分。三条各占了一个评审席位。
成因：`needsEnrich` 那条「thread 且 feed 已给内容就不补全」只保护得住 Discourse
（RSS 里就是首帖全文）；V2EX 的 tech.xml 给空内容，于是走补全，补回来的是整页。
**规则本身合理，喂给它的输入却来自「怎么抓」而不是「抓到什么」——和 `FORUM_SHARE`
那次是同一个形状。加任何基于长度 / 篇幅的判据前，先确认量的是不是作者写的那段。**
现在 `threadBodyHtml()` 三态返回：切得到首帖给 HTML，切不到给 `''`（确认为空，
不许拿整页顶上），没有切法的站给 `null` 走原路。

**「落点在结尾」的判据，必须确认你手里那段字符串真的是结尾。**
2026-08-20 量到的第三例「规则合理但输入由怎么抓决定」（前两例是 `FORUM_SHARE` 按 kind 判、
论坛篇幅量整页）。`SELF_PROMO` 的结尾分支看的是 `excerpt.slice(-400)`，
而 `excerpt` 是 `extractArticleText(html, 2500)` 的产物——**正文一旦超过 2500 字符，
那 400 个字符就是正文的腰**。当天 36 个入围条目里 19 条（53%）被截断，
这条判据对它们从上线起就没生效过，而自荐帖的招呼语恰恰压在最后一段
（「MIT 协议开源，欢迎 star」「以上文章均可在我的个人博客找到」「新用户 300 万免费 token」）。
现在抓取层单独带回 `tail`（正文最后 400 字符，没截断时为空串），判据用 `tail || excerpt.slice(-400)`。
**通用判据：任何按位置取样的规则（开头 N 字、结尾 N 字、首帖、前 20 篇），
都要先问一句「我取的这一段，是不是我以为的那一段」——截断、分页、页面 chrome 都会让它错位，
而且一律不报警。**
配套的一半同样重要：管道修好之后**词表往往还没跟上**。同一天把 19 条的真结尾逐条打出来，
按现行词表分数一条都没变，因为表里只有「求 star」没有「欢迎 star」。
**修完取样口径要立刻拿新样本重量一次词表，否则修的是一条仍然扣不到人的规则。**

**源出问题和「这个源的某类帖子出问题」要分开。** 承上：8-09 那天 V2EX 5 条入围全废，
但账是这么算的——创刊以来收录 64 篇里 V2EX 占 13 篇，最近 7 天有 5 天各出 1 篇、
其中 3 篇 5 分。要动的是「纯标题帖也能进名单」，不是这个源。
和 BestBlogs 那条对照着看：那条是**整源结构上永远不会有**（摘要页），所以整源降级；
这条是**一个源里的一类帖子**，所以修判据。判据：问「这个源明天还可能出好东西吗」。

**机械去重分不开「同题材的烂文」和「同工具的好文」。** 已调查，别重试：

| 方法 | 真重复组内最低 | 无关文章最高 | 可分离 |
|---|---|---|---|
| 标题二元组 Jaccard | 0.22 | **0.30** | ✗ |
| 剥掉工具名后比标题 | 0.05 | 0.15 | ✗ |
| 正文二元组 Jaccard | **0.03** | 0.40 | ✗ |

三种方法里真重复的相似度都低于真正不同的文章——因为它们不是复制，
是同一个 SEO 选题的独立改写。代码已删。同选题只留一篇，靠人读。

**但「相似度分不开」不等于「同一篇也分不开」，这两句话之间隔着一整道闸。**
上面那条讲的是**同题材的不同文章**，而**同一篇的标题逐字相同，用不着相似度**。
这条判据 08-19 先用在了「已经出过刊的那篇换个 URL 又来一次」（`publishedTitles`）上，
2026-08-29 才发现它只做了一半——挡不住**同一轮里同一篇占掉好几个席位**：
当天 474 条原始条目里有 7 组严格同题、多吃 11 个席位，最大一组是掘金一个作者
把同一个标题发了 6 遍，其中 4 条进了当日 43 席的入围名单，**评审预算的 9%
花在同一篇上**。误伤量过：创刊以来 175 条已收录条目里严格同题 0 组。
**配套的一条比规则本身更容易写错：只比严格同题，不比作者。**
那 7 组里有 2 组的 `author` 一边有值一边是空串（同一篇同时从平台和作者自己的 feed 进来），
要求同作者恰好会漏掉最该挡的跨源转帖——**作者字段的有无是「哪个源给的」，
不是「谁写的」**，拿它当判据的一部分，等于又一次把「怎么抓」当成了「抓到什么」。
（收益要如实记：当天腾出的 4 个席位补进来的 4 条一条都没收，**净收录 0**。
这条改动换的是候选质量不是收录数，别拿它当增产手段。）

**配额规则要验证它真的按写的那样跑，别只读代码看它「像是对的」。**
`FORUM_SHARE` 和 `PER_SOURCE_QUOTA` 两条都写得很清楚、注释详尽、有测试，
但 2026-08-04 之前从来没有在真实数据上同时生效过：
论坛席位取的是「文章填完 cap 之后的余量」，文章型源自己够 60 条那天恒为 0
（59 条文章时论坛能拿 39 席，60 条时归零——断崖式跳变是这类 bug 的指纹）；
`byQuota()` 的补位轮不再读 `used`，按源配额对高产源等于不存在。
后果是当天分数最高的一条被判「已达占比上限」，而掘金一家吃下 45/60 席。
**已有的测试全都通过**——它们测的是规则的意图，不是规则在真实分布下的行为。
每条配额规则至少要有一条测试模拟「某一类供给压倒性多」的极端分布。

**席位的期望产出不同时，该调的是分配不是分数。** 2026-08-10 把创刊以来每天的
`_pending.json` 和当天日文件对了一遍：`thin: true`（补全失败、只剩标题）的席位
54 个换回 2 条收录（3.7%），非 thin 的 148 个换回 31 条（21%）；
而那 2 条还是编辑手动重抓正文之后才收的，不是靠标题收的。
一个 thin 席位值普通席位的六分之一，却吃掉同样的评审预算。
但**不能给 thin 扣分**——thin 是补全被限流的结果，是「怎么抓」不是「抓到什么」，
按它扣分就是第三次踩 `FORUM_SHARE` / V2EX 首帖那一脚。
所以分数一分不动，只封名额（`THIN_SHARE = 0.25`，`THIN_FLOOR = 3`），
和 `summaryPage` 同一个层次。名额要切在**配额分配之前**，
腾出来的席位才能让原本被单源配额挤掉的能读条目补进来。
地板不设 0 的理由和 summaryPage 正相反：摘要页是结构上永远不会有，
thin 是偶发的管道故障，明天可能就通了；且 8-05 那两条 thin 收录在 thin 内部分数排前二，
按分数留前几席一条都不会丢。

**落选理由是给下一个你看的诊断，写错了会把手术做在错的地方。**
2026-08-22：22 条掘金条目（最高 9 分）全部记成「超出当日入围上限」，
而当天名单只有 49 条、cap 是 60——**名单根本没满**，挡住它们的是
`quota * QUOTA_RELAX` 那道单源闸。照字面读这条理由，下一轮会去调 cap，
而该看的是配额。成因是那句理由写成了 `isForum(item) ? 占比上限 : 入围上限` 的二选一，
根本没有「配额」这一档。**凡是被规则挡下的条目，理由字符串要能一眼分出是哪条规则挡的；
它本身也是数据，它错了，后面所有基于它的判断都会跟着错。**

**`seen.json` 那本账也要过「记的是结论还是记的是一次没排上队」这一问。**
08-21 / 08-22 那两条讲的是作者个人站的账本，2026-08-23 发现同一个病在系统的核心账本上，
而且更贵。`tinker-fetch` 对**每一条**写进 `_pending` 的条目都记 seen——被规则毙掉的也记，
这一半是对的（否则每天把同一批噪声重抓一遍、重扣一遍分）。错的是另一半：
**被名额挡掉的也一起记了**。两者含义正好相反：分数不够、命中反向词、是摘要页、是转帖，
这是对这一条内容下的**结论**，明天再判还是同一个答案；而「单源配额已满」「超出当日入围上限」
「thin 名额已满」跟这一条是什么毫无关系，它说的是**当天的供给结构**。
当天量到的代价：入围名单只有 29 条（cap 60，**空着 31 席**），却有 19 条 6-10 分的掘金条目
被 `quota * QUOTA_RELAX` 那道单源闸挡下、就此永久出局；被 thin 名额挡掉的另有 37 条，
而它们 thin 只是因为那天掘金限流、补全熔断——明天补得回来就不是 thin 了。
**席位空着不要钱，永久丢掉一条是不可逆的。**
改法不是放宽配额（逐条看完那 19 条，一多半确实是内容农场文，
「入围名单是评审预算」那条没有错），而是让名额落选**不写结论**：
`triage()` 给这类落选标 `gated`，抓取层不记 seen，改记进 `tinker/data/deferred.json`
攒轮次，攒够 3 轮仍没排上队才落成结论（三态：结论 / 待定 / 没抓成）。
**通用判据升级：一份「记下来省得下次再做」的账，除了问「这一条记的是结论还是一次失败」，
还要问「记的是不是其实只是一次没排上队」——排队结果是当天供给的性质，不是这条内容的性质。**

**而「没排上队」这一格里还藏着第三类：有一道闸量的根本不是排队，是我们没读到。**
2026-08-27 量到的，是上面那条判据的第三次分叉（结论 → 失败 → 没排上队 → **没读到**）。
`triage()` 的四道名额闸里，`quota` / `cap` / `forum-share` 说的都是「名单里挤不下」，
攒够 3 轮认了没错；**唯独 `thin` 不是**——一条条目 thin，是因为它的源那一轮被
`enrichPass()` 熔断了，请求有一多半压根没发出去。
LESSONS 早写死了「不能给 thin 扣分，thin 是『怎么抓』不是『抓到什么』」，
**而 thin 名额的计数也一样，只是这句话当时只落到了打分那一半。**
当天的账：59 条被名额挡下，52 条是 thin，**其中 47 条是掘金**——而掘金正是当轮
探针 40 发 0 中被熔断的那个源，第二轮 103 条救回 0。挡下的里面有
「7 万星仓库教的安装路径是错的——整理 130 个 AI Skill 的踩坑记录」（10 分）、
「Hermes 模型路由崩溃实录」（8 分）这种正对选题的条目；掘金连限三天，
它们会在**一次都没被读到**的情况下永久出局，而账本上写的是「攒满 3 轮没排上队」。
改法：`planSeen()` 收一份 `mutedSources`（抓取层已经算出来的 `enrichMuted`，不是猜的），
`gate === 'thin'` 且源本轮被熔断就**不计一轮**，只记 `stalls`。
**三条边界一条都不能省**：(1) 熔断只保护 `thin`，它对「名单挤不挤得下」没有解释力，
同轮被配额挡的照常计；(2) 保护有 TTL，过了窗口照常计数——否则一个永远限流的源
会把尾巴永远挂在账本上，那就从「永远不再来」翻到了「永远重来」；
(3) 源恢复供货之后同一条还是 thin，那才是对它的结论，照常攒轮次。
**通用形状：给一个计数器加「这一轮不算」的豁免之前，先问它豁免的是哪一道闸——
豁免理由只对提出它的那道闸成立，套到别的闸上就是给噪声开后门。**

**一份账本记「攒够几轮」时，轮次要按闸门分开记——阈值可以不分，诊断必须分。**
2026-08-26 补 `deferred.json` 时收的。`planSeen()` 原来每条只记 `{ first, attempts }`，
于是「被单源配额挡两次 + 被 thin 名额挡一次」和「被同一道闸连挡三次」是同一个 `attempts: 3`。
判死的阈值不用因此改——三天里供给结构确实换过了，它仍然没排上，这一条没错；
**错的是账本答不出「这批永久出局的条目死在哪道闸上」，而那是下次该调 `SHORTLIST_CAP`
还是调 `PER_SOURCE_QUOTA` 的唯一依据。** 改完当天就结出一份账：37 条被名额挡下，
**32 条是掘金的单源配额、5 条是 thin、cap 一条都没有**（名单 35 条，cap 是 60，根本没满），
正是 08-22「照字面读那条理由会去调 cap，而该看的是配额」的第一份直接证据。
**通用形状：凡是「攒够 N 次就下结论」的计数器，都要问一句这 N 次是不是同一件事；
不是的话，阈值可以照旧，但每一次是什么必须留下来。**

**「分母里混进了没参与的那部分」的第四次复发，而这次分母长在诊断输出上。**
前三次分别是限流截断后「整源失败」的分母、`seen.json` 里把「没排上队」记成结论、
thin 名额在熔断轮照记轮次——都是抓取那一侧。2026-09-01 的这次错在**下结论的那一侧**：
08-31 给 `MACHINE_REPORT` 留的待办是「看它明天挡到几条；连着几天 0 命中就说明模板换了」，
09-01 它 0 命中——而这条规则是照着**掘金那批稿子的正文免责声明**写的，
当天掘金补全熔断，**121 条里 76 条是 thin（63%）**，那批正文根本没进过语料。
`命中 0 / 406` 这个数字上，「模板换了」和「今天没读到正文」长得一模一样。
**判据：量一条读正文的规则，分母必须是可读语料（`total - thin`），
而且要按源报 thin 占比——规则通常是照着某一个源的模板写的，那个源哑了，它今天就没有考场。**
改法照「一条每天靠记性重新量的规矩不会收敛」那条，交给机器：
`lib/tinker/corpus.mjs` 的 `readableCorpus()`，抓取尾部和 `--probe` 都固定打这几行，
条数 ≥10 且 thin ≥50% 的源标成「没有考场」。
**推论：一条规则「连着几天 0 命中」的计数，要把它的语料哑掉的那些天剔出去再数。**

**「作者名的形状」是条诱人的判据，但先去看它留没留在账本里。**
同一天量的另一条：掘金的 SEO 推广稿有个极便宜的机器特征——作者名是默认的
`用户88858179903` 这种「用户+数字」。当天 3 条命中全部是该毙的。
按老规矩查误伤，**当场被数据挡回来**：创刊以来 34 条已发布的掘金条目里有 2 条
（08-01 的 CLAUDE.md 那篇、08-04 的 Qoder 那篇，都是 4 分）作者正是这种默认名。
挡 3 条误伤 2 条，和 `低价` / `免費額度` 同族——**看起来该加，实测误伤的比挡住的多。**
**配套一条口径限制**：`rejected` 只留标题和判据、不留 `author`，
所以这一问只能在当天的入围名单上量（406 条全库里只有 22 条带作者名）。
**凡是要拿某个字段当判据，先确认落选那一侧还留着这个字段——否则你只量得到入围的那一半。**

**入围名单是评审预算，不是必须填满的额度。** 修上面那两条的代价是
名单在「只有一个源有货」的日子会变短（2026-08-04：60 → 36）。这是要的结果：
36 条干净候选比 60 条里混 29 条内容农场文更好评。
遇到「改了规则名单变短」时不要回头放宽，先看短掉的是什么。

**不要为了「名单成分好看」不断加配额规则。** 入围名单只是给评审用的候选池，
真正的过滤在编辑那一步。某个源占得多，只要评审挑得散就没问题；
而如果那天只有它有货，砍掉反而更糟。这是这个项目里反复出现的诱惑。

## 抓取与正文

**去标签不能用 `/<[^>]+>/g`。** 属性值里合法出现 `>` 时它会在标签中途收尾，
把标签后半截当正文吐出来。真实例子是 Discourse 的响应式样式表
`<link media="(width >= 40rem)" ...>`，一个页面几十条这种碎片，
导致 linux.do 的中文帖被判「中文占比 1%」全部毙掉。
同一个正则反向也错：正文里的 `1 < 2 且 3 > 2` 会被吃成 `1 2`。
现在按标签内引号状态扫描，只认引号外的 `>`；一直没闭合的 `<` 当普通字符放回。

**实体转义过的 HTML 解码后要再去一次标签。** 有的 feed 把整段 HTML 转义后塞进
description（BestBlogs.dev 就是），解实体是在去标签之后做的，
于是每条摘要开头都是一大段 CSS。第二遍必须**不再解实体**，
否则 `&amp;lt;` 会被解两层变成 `<`（正确结果是 `&lt;`）；
用「解码结果里出现闭合标签」作为触发条件。

这两条都在共用的 `lib/html-text.mjs` 里，**信源罗盘也受影响**，改动要跑全量测试。

**补全失败不都是反爬，很大一部分是限流，隔一会儿再要就给。**
2026-08-05：16 条掘金入围条目全部 `thin`，而 thin 在评审那一步是**一律不许收**的，
等于最大供给源在评审之前就已经失去收录资格。查下来掘金返回的不是 JS 挑战页，
是 `HTTP 200 + x-tt-system-error: 3` 的 2397 字节错误页——Googlebot / curl /
完整 Chrome 三种 UA 拿到的字节数**一模一样**，和身份无关。隔几分钟按 4 秒间隔重放，
9 条拿到完整正文，其中 2 条当天收录（当天收录量的 40%）。
**但重试要克制**：紧接着按 3.5 秒、9 秒又跑两遍，两遍都是 0 收获，限流被打得更死。
现在是「等 60 秒补一轮、并发减半」，不是「重试到成功」。
判据：**返回体字节数在不同 UA 下完全相同 = 服务端状态问题，值得重试；
字节数随 UA 变 = 反爬，重试没用。**

**限流类故障的恢复是概率性的，别拿「连着几天零产出」判它永远不会有产出。**
掘金正文补全的第二轮重试在 08-08 / 09 / 10 连续三天 `enrichRetried: 0`，
08-10 的复盘写了「明天如果还是 0 就改触发条件或直接停掉」；
**08-11 它救回 5 条**（211 条重试）。这和 08-08「首页也挂 = 站点真死」被证伪是同一种错：
拿几次观测去给一个概率性的东西下确定性结论。
判据：**成本可忽略且失败无副作用的重试，不该按连续零产出砍**——
它的代价是一轮 60 秒等待，而砍掉之后错误再也无法自我纠正。

**但「失败无副作用」是有条件的，条件是次数少。** 2026-08-12 掘金 285 条原始条目
里 284 条抓不到正文，第一轮 285 个请求换回 1 条，第二轮 291 个换回 0 条——
**一个源吃掉当轮 85% 的补全预算**。故障类型没变（还是那个 2397 字节的
`x-tt-system-error: 3` 限流页，手动 curl 三篇复现，字节数一模一样），
变的是量级：掘金从一天几十条涨到两百多条，于是「明知在限流还是一条条问完」
的代价从几十个请求涨到几百个。而上面那条 08-05 的记录里明写着
「同一轮里接着重放两遍，两遍都是 0 收获，**限流被打得更死**」——
两句放一起，结论就变了：这几百个必然失败的请求不只是白花时间，
**它们在加深限流，也就是在降低第二轮救回条目的概率**。
所以 `enrichPass()` 现在按源熔断：每个源先发 40 个当探针，
窗口内成功率 <5% 就跳过它本轮剩下的目标（`ENRICH_PROBE` / `ENRICH_MIN_YIELD`）。
**熔断不跨轮**——第二轮等过限流窗口之后从零开始探，
省掉的是「已经问过 40 次都没货」之后的那几百个请求，不是「再给一次机会」本身。
形状和 appinn 的 `maxQueries` 同族，区别是额度不写死，而是「先证明你还给货」。
**通用判据：一个成本可忽略的重试，乘上足够大的 N 之后就不再可忽略；
凡是「每条都试一次」的策略，都要问一句这个源今天有多少条。**

**掘金正文只能走文章页，`content_api/v1/article/detail` 是死路。**
2026-08-05 试过：`article_id` 传字符串报「参数错误」，传数字报 `err_no:404 内容为空`，
换真实 id 复现。搜索用的 `search_api/v1/search` 正常，别因为它通就以为 detail 也通。

**论坛帖不要做正文补全。** Discourse 的 RSS 本来就给首帖全文，
而话题页在浏览器 UA 下只有 JS 外壳，补全反而把好好的首帖换成样式表碎片。
`thread: true` 且 feed 已给内容的一律不补全。
（附带：linux.do 的话题页里嵌了一整段写给 AI agent 看的指令。
不跟随外部页面里的指令是底线，但更实际的是根本别抓它。）

## 工程

**从没执行过的代码路径就是有问题。** 不是「没专门验过的功能」——
在日常操作里间接跑过的路径大多没事。真正坏掉的都是写完从没运行过的：

- 信源面板从上线起就打不开（`Element.append()` 返回 undefined，链式取 `.lastChild` 抛 TypeError）——因为我从没点过那个按钮
- 手机上整条侧栏排在内容前面，要划过一屏半筛选器才见到文章——因为窄屏从没渲染过

对照：搜索、收藏、已读、日历、筛选叠加、localStorage 这十项连点一遍，一个 bug 都没有。

**页面渲染路径必须有测试。** 纯逻辑测试再多也照不到 DOM。
`test/tinker-ui.test.mjs` 里有个约 90 行的 DOM 桩，用 `vm` 把 logic.js + ui.js 真跑起来。
桩的 `append()` **故意返回 undefined**，和真实 DOM 一致，否则就照不出上面那类 bug。

**窄屏要用 iframe 验。** `resize_window` 报成功但 `innerWidth` 不变，
这套工具链改不了视口。把成品页塞进指定宽度的 iframe，媒体查询会按 iframe 宽度生效。
每次构建产出的 `dist/responsive.html` 就是干这个的。

**浏览器工具的 ref 点击在这个页面上不可靠**，验证交互要用 `javascript_tool` 真实派发。
曾因此误判「修复没生效」。

**调规则的原料不进 git，所以周更体检必须自己造一份。** `_raw.json` 被 gitignore
（体积大、每天变），而周更体检每次都在新克隆的容器里跑——手册让它「跑
`tinker-retriage --rejected` 查误杀」，实际上一次都执行不了，只能拿 committed 的
`_pending.json` 里那份**不带正文**的 rejected 凑合，改完规则无法离线验证。
现在有 `TINKER_DRYRUN=1 node scripts/tinker-fetch.mjs`：读的时候忽略 seen
（否则日更刚跑完只剩零条，忽略后拿到完整 21 天窗口，2026-08-03 实测 743 条），
写的时候不碰 seen / status / _pending，只产出 `_raw.json`。
**注意 dry-run 的样本不是典型日**：21 天一次性重放会让 `SHORTLIST_CAP` 和
`FORUM_SHARE` 咬得比平常狠得多，查误杀时要先把「占比上限 / 入围上限」这两类
理由滤掉，剩下的才是规则真正毙掉的（当天 683 条里只有 648 条是规则毙的）。

**量一条按位置取样的规则时，语料的取样口径必须和规则一致，否则误伤会被藏起来。**
这是 08-20「我取的这一段是不是我以为的那一段」的第二只靴子，2026-08-21 自己踩了一次：
量上面那条「仓库链接形」时先拿 `excerpt` 当语料，报出来 **0 误伤**；
换成 `tail` 才看见误伤的是当天的 5 分精选。原因就是同一条——
`excerpt` 截在 2500 字符，被截掉的那一半正好是结尾。
**修好了取样口径的规则，如果还拿旧口径的语料去量，等于什么都没修。**
`scripts/tinker-retriage.mjs --probe <正则>` 现在把三个口径
（标题+开头 400 / 真结尾 tail / 全文 excerpt）分开报，并自动拿已发布的日文件对一遍，
命中里出现已收录条目就直接标成误伤。加词前先跑它，别再手写一次性脚本。
（注意「真结尾」那一行的分母只有正文超过 2500 字符的那批，2026-08-21 是 98/448，
命中一两条时样本量本来就不够。）

**`seen.json` 是共享状态，本地跑 `tinker-fetch` 不是只读操作**——
它会消耗云端那轮的原料。规则实验只用 `tinker-retriage`（离线重放，不写 seen）。
踩过一次：本地测了三次抓取并提交，把 27 条候选（含 5 分精选）从云端那轮手里吃掉了。

**`--merge` 类操作必须在写入时重算去重集合**，不能只信启动时那份。
同一脚本跑两次会把同一批源追加两遍。

## 编辑

**及格线 4 分，3 分及以下一律不收。** 起因是创刊号收了 29 篇、其中 13 篇是 3 分，
那 13 篇几乎全是论坛的自荐帖和短讨论，整个列表因此显得很水。
宁可某天只有 3 篇。

**自荐帖和真折腾的区别在落点**：落在「让你去用它」（功能列表、求 Star、欢迎试用、
官网链接）是自荐；落在「我为什么需要它、踩了什么坑」才是折腾。
招呼语可能压在结尾，只看开头会漏。

**「有真发现」也可以是自荐帖，和「干货是真的」那条同族。** 2026-08-18 的
「装 DSH 插件时发现疑似后门」：开头是货真价实的发现（插件读本地凭据、取环境变量、
往外部地址发数据，文档里一个字没写），结尾落在他自己的三个东西上——
插件、目录站、安全扫描器，外加「欢迎大佬们拍砖」。
**判据仍然只有落点，不因为开头那段发现足够硬就动摇。**

**自荐词表的三种漏法，一种都不是「判据不对」，全是同一句招呼语的写法没写全。**
2026-08-18 DSH 发布周，57 个入围席位里 13 席是自荐帖，`SELF_PROMO` **一条都没扣到**。
逐条查下来是三处：(1) `\[开源\]` 早在表里，而 linux.do 的标题写的是**全角**的「【开源】」；
(2)「欢迎大家」在论坛里的常见写法是「欢迎大佬」；(3)「请大家锐评一下」「欢迎拍砖」
「提提意见」这一整类征求意见的招呼语没有，尽管同义的「求反馈 / 求建议」在表里。
第一处和「每加一个新字形的源，回头把所有中文正则查一遍」是同一个洞，
**只是这次换的不是简繁，是半角/全角括号**——凡是正则里写了 ASCII 标点
（`[]`、`()`、`""`、`:`）的地方，都要问一遍中文全角写法在不在。
补完之后按老规矩量过：唯一新增命中 6 条全是当天毙掉的，收录的 8 篇 0 误伤。
**发现某类噪声占了名单一大块时，先查这类噪声在 `preReasons` 里被扣过几次；
「规则拦不住落点」是真的，但「规则连字面招呼语都没匹配上」是另一回事，别混为一谈。**

**「结尾挂自家仓库链接」不是自荐的判据，配套的那句招呼才是。**
2026-08-21 差点把它写进 `SELF_PROMO`：当天手工挑的候选形状是
`(仓库|项目地址|开源地址|项目就在这)[:：]?\s*github/gitee`，看着极像落点。
实测 3 条真结尾命中里 **1 条是当天的 5 分精选**——银古那篇 OpenCode 配置重构，
结尾就是干干净净一行「项目地址：github.com/znlgis/my-opencode-deepseek-config」，
什么都没求。被毙的那几条与它的差别不在有没有链接，在链接旁边那句冲着读者说的话
（欢迎试用 / 拿去用 / 帮我看看 / 评论区见 / 推荐标签），而那正是这张表本来就在做的事。
**判据落在「有没有让你做点什么」，不是「有没有指给你一个东西」。**

**而「让你去用它」不只有一种卖法：还有一类卖的是课程和教练服务。**
2026-08-16 vocus 接进来第二天量到的：13 个入围席位里 5 席是同一类东西——
作者签名带「AI賦能師」，正文讲「我帶的學員 / 一日實戰工作坊」，
卖点永远是「每天為自己贖回 2 小時」，结尾是「歡迎按愛心、收藏並分享」。
它们确实在讲用 AI 干活（和 TRAE 投稿潮那条一样，「干货是真的」不影响判断），
但落点是来上我的课。已经前移到规则层（`COACH_PROMO`，扣 6 分不硬毙）。
**两条配套的经验**：
(1) 选词时试过 `一人公司` 又拿掉——它是正常的商业概念，当天就误伤了一篇讲电影的稿子；
去掉之后 390 条里命中 10 条、10 条全对、0 误伤。**加负向词也要过「它本身是不是别人的词」那一问。**
(2) 同时发现 `SELF_PROMO` 整张表**在繁体语料上从来没有命中过一次**
（当天 56 条繁体条目，命中 0）——那张表是照着简中论坛语料写的，
而 vocus 和 iT 邦幫忙现在合起来占入围名单四分之一。
**每加一个新语种 / 新字形的源，都要回头问一遍现有的负向词表在它上面还灵不灵。**

**一条没有单位的数值规矩，永远不会收敛——而症状是「每次复盘都在重新量同一件事」。**
「量一件事要用系统自己的那把尺」这一族已经记了四例（评分器、匹配器、诊断工具、取样口径），
2026-08-30 是第五例，也是最钝的一种：**根本没有尺**。
手册的摘要字数写着「250-450 字」，从创刊起就没说过一个「字」是什么。
拿已提交的日文件复量 08-29 那批 9 条：按**全部字符**中位数 503，按**汉字**中位数 239——
前一种读法说「几乎每条都超上限」，后一种说「几乎每条都不到下限」，
**同一份语料，两个相反的结论**；而当天 REVIEW 里记下的那串数字（476/481/462/…）
和这两种读法都对不上，也就是说它量的是第三种口径。
这解释了为什么这条规矩改过三次、REVIEW 连记五天仍然「改完还是对不上」：
**每一天量的都不是同一个量，所以每一天的结论都真实，也都没法叠加。**
（08-29 的结论「超区间的 8 条全是机制型，把上限抬到 500」尤其危险——它是从一天的样本里
读出的一条漂亮解释，而 08-30 的 4 条超区间条目里 3 条不是机制型，
解释当场就不成立了。**一个量错了单位的分布，仍然会长出看起来很讲得通的因果。**）
改法有两半，缺一半都不管用：(1) 把单位钉死在手册和代码里（`[...s].length`，
数字、英文命令、标点都算，理由是它们占的是同样的阅读带宽）；
(2) **把量这件事交给构建期**，每次构建打出当天的条数 / 最短 / 中位 / 最长并点名超区间的。
第二半是重点——**一条每天靠记性重新量一遍的规矩，五天里被重新量了五次也没收敛；
交给机器之后它才会停止被重新讨论。**
**通用判据：凡是手册里写死了一个数的规矩，先问它的单位是什么、谁来量；
两个问题里有一个答不上来，这条规矩就还没真正生效，改它的数字是在做无用功。**

**AI 编造的伪深度文比软文更该毙。** 软文只是没营养，这类是把错的东西说得像实测。
识别靠核对可验证的机制事实，不是靠文风：2026-08-04「Claude Code深度解析」
写它「启动时深度扫描仓库建索引，存进本地向量数据库（SQLite + 向量扩展）」——
不建索引恰恰是它区别于 RAG 路线的核心；同一天「32 个亲测技巧」写
「把频率惩罚从 0.5 调到 1.5」「MCP（预配置模型）」「上下文窗口调到 4096 tokens」，
参数和名词全是编的。**凡是通篇没有一个能对得上的版本号、报错原文或文件路径的
「深度解析」，先假定是编的。**

**它的近亲不编造，反而在正文里写明「我没有运行过」——而这句话本身就是判据。**
2026-08-31 掘金冒出一整批「GitHub每日热评｜X 源码解析」（署名一律
「Valhalla Matrix治理实验室」），一天吃掉三个入围席位，分数还是当天前几名：
选题极其对口（openai/codex 源码、Rust 的 ai-memory、Playwright CLI），
工具词话题词命中密集，正文里全是「扫描范围内文件数 6432」「测试文件线索 647」
这类看着很硬的数字。**和上面那条不是一回事**：那一类是把错的说得像实测，
只能靠核对可验证的机制事实认；这一类的数字大多是真的，问题在于没有人动手，
而它自己在开头和结尾把这件事写得清清楚楚——「本文基于指定源码快照进行静态分析」
「本文未执行源码、测试、构建、依赖漏洞扫描或生产环境部署」「本文结论类型：源码静态观察」。
一篇明说「我没有运行过」的稿子，按定义就不是「作者自己动手做了什么」。
这是这个项目里少见的**字面即判据**的情形，所以敢做成规则（`MACHINE_REPORT`，扣 6 分不硬毙；
三个口径命中 3 / 2 / 3 条，拿创刊以来的日文件对过，已收录条目 0 误伤）。
**但边界要一起记住**：同一天还有一篇【OpenAI Codex CLI 深度技术分析报告】，
一望而知是同一个生成器的产物（`00. Executive Summary`、结尾整行
`Evidence(✅ 关键结论均有源码或一手资料支撑)`），**只是没写那句免责**，规则挡不住。
和「推广稿会脱掉容易认的外衣」是同一条：**规则挡的是这一批稿子当前的模板，
不是这一类内容**——所以这条规则一旦连着几天 0 命中，该记的结论是
「模板换了」，不是「这类噪声消失了」。

**软文的下一形态：正文纯方法论，落点藏在页脚的「相关阅读」里。**
2026-08-08 轶哥「用多Agent搭建更可靠的合同审查智能体」：两千多字全是方法论
（5 个角色分工、权重分配、状态返回、失败标签），读起来完全像一手经验，
连 8-06 那批 TRAE 稿的「维度对比表」都没有。判出来靠三件事同时成立：
**通篇没有一个工具名 / 框架名 / 模型名**、「实际收益」一节全是
「明显少了」「更直接」这种定性表述、而结尾「相关阅读」链向自家产品
DesireCore 的官方文档和「合同审查 Skill 示例」。
**判据升级：没有任何一个具体工具名的「实践文」，先去翻它的页脚和相关阅读。**
（对照：站点级页脚广告不算软文，见下面那条；区别在链的是不是文章正文在推的那个东西。）

**聚合站的 AI 摘要页不收，理由是页面性质而不是内容质量。**
`bestblogs.dev/article/<id>` 这类页面本身是站方生成的摘要，不是作者原文。
收它等于把读者送到二手摘要页，而 `summaryZh` 里的每一句也只能来自那份摘要——
够不着「不许编造」那条线，但已经踩在「转载而无本人补充」上。
2026-08-04 因此毙掉一篇内容相当硬的 TencentDB Agent Memory 实测。
想要这类内容，正确做法是去接**原文源**（那篇的原文是 Datawhale），不是收摘要页。

**「整源永远不可能入选」和「这个源最近没货」要用不同的尺子。**
2026-08-08：BestBlogs.dev 创刊 7 天，天天 2-3 条进入围名单，**累计收录 0 条**。
「连续 30 天零入选才清理」那条挡了它 7 天，但那条保护的是
「今天没货、明天可能有」的月更博主，而摘要页是**结构上永远不会有**。
现在这类源标 `summaryPage: true`：照抓、照打分、照进 `rejected` 留痕，
只是不占入围名单的席位。**留痕这一半是重点**——它的落选条目就是
「该去接哪个原文源」的线索表。
推广开来：**发现某个源被一条编辑规则整类挡住时，该做的是把这条规则前移到规则层，
而不是每天在评审那一步重新毙一遍。**评审预算是这个项目最稀缺的东西。

**判「结构性」不用等，逐条看它近 20 篇的形状就够了——而这一问要在设留存表之前问。**
2026-08-25 的第二例：x-cmd 前一天刚被换了 feed（订错成英文站，见上面「订的是不是中文那一份」）
并设了 30 天的表，当天它就吃掉 3 个入围席位、3 条全毙。逐条看它近 20 篇：
**16 篇是「TLDR + 阅读原文」的他人文章摘要卡，4 篇是自家功能公告
（`x codex ds` / `x keyring` / `x repo`），一篇作者自己动手的记录都没有。**
和 BestBlogs 同形，当天就标了 `summaryPage: true`。
关键在于这个判断**不需要那 30 天**：30 天量的是「有没有货」，
而形状问的是「有货的时候它长什么样」，后者一次采样就能答。
**次序：给一个源设留存表之前，先花五分钟扫它近 20 篇的形状；
是结构性的就当场前移到规则层，别让它在观察期里每天白拿几个评审席位。**
（配套：`summaryPage` 这个字段名说的是「摘要页」，但它真正标的是
「落地页在结构上不可能是作者的一手记录」——聚合站的 AI 摘要页、
「TLDR + 阅读原文」的转述号、产品方写自己产品的官网博客，都归它管。）

**系列文章按单篇判，不能因为系列主题对就整系列放行。**
「从 PHP 到 AI + Golang 转型手记」8-01 收了（四十六），8-04 的（四十九）
讲的是 Golang 筛选字段白名单和 SQL 注入防护，agent 只出现在
「这里直接让 AI 检查」一句里，毙掉。回头看（四十六）那次多半也偏松了。

**转述得越具体越危险。** 2026-08-05「运维 Agent 选型踩坑实录：Hermes vs OpenClaw」
标题、结构、数字（2 秒启动 / 50MB vs 300MB+、RAG 检索命中率不到 30%）全都长得像
一手实测，但第一句是「最近有个朋友找我吐槽」，第三句是「磨了他一下午，
总算把故事挖出来了」——整篇是转述。**具体本身会被误当成一手证据**，
所以判「作者有没有动手」要看人称和信息来源，不能看细节密度。

**站点级页脚广告不等于软文，区别在广告是不是文章的落点。**
2026-08-05 收了 zelikk 那条（指挥 agent 给 Telegram Web 加功能），
尽管页脚挂着 VPS 返利链接——那是这个博客每篇都有的站点级页脚。
对照：教程软文的判据是**正文结尾**在推中转站 / 镜像站 / 会员渠道。

**技术含量高但选题不该收的，要写清「不是质量问题」。**
2026-08-05 毙了 linux.do 那条给 Claude Code 命令安全分类器打 fail-open 补丁的帖子，
它是当天论坛帖里技术含量最高的（settings.json 的 env 只对 `ANTHROPIC_*` 生效、
minified 里的 `Og` 是空对象快照、cli.js 的 `using` 语法要 Node≥23，都是真啃过二进制）。
不收的理由是这本刊物不该把绕过安全闸门的配方放首页，起因还写着「让 flash
帮我搞一下 grok 注册机」。**这类要在 REVIEW 里写明理由**，否则下次会被当成漏评补收。

**有真踩坑也可以是软文，判据仍然只有落点。** 2026-08-06 掘金出现一波 TRAE 投稿潮
（有一条标题直接带 `#TRAE Work 实战帮` 话题标签），6 条格式统一：先摆一张
「维度对比表」（对手全「良」、它全「优」），中间夹一段**真实的**踩坑
（WSL2 只读、CUDA 版本对不上、`.bashrc` 一行带续行符的 PATH 赋值把 PATH 覆盖成残缺值），
落点是「国内直连、基础版免费、数据合规」。这批比以往的软文难认得多，
因为它们确实动过手。**不要因为「干货是真的」就动摇——看结尾往哪走。**

**规则层拦不住落点。** 收录率低不一定意味着规则太松。2026-08-06 收录率 12%，
但 33 条入围里 6 条 TRAE 投稿 + 5 条中转站/自荐 + 2 条聚合站摘要页——
那 6 条每一条都真的在讲用 agent 干活，权重和反向词拦不住它们，
**分辨落点本来就是评审那一步的活**。看到收录率低时先看短掉的是什么，
再决定动不动 `relevance.mjs`。

**一条扣分规则的分值要按它要挡的那批稿子的裸分定，不是照别的规则抄。**
2026-09-06 加「选型盘点体」那条时差点犯的错：照 `SELF_PROMO` / `MACHINE_REPORT`
的惯例扣 6 分——而目标那三条掘金软文的裸分都是 13（标题命中 multi-agent 6 + 泛词 1 +
标题经验词 3 + 正文经验词 3-4），扣 6 之后是 7 分，仍在入围线（6）之上。
**这种「扣了但没改变任何结果」比没写规则更坏**：它会在 `preReasons` 里留下
「规则命中了」的痕迹，下一轮复盘看着它就以为这类噪声已经处理过。
改成 8 分，离线重放三条全部跌出名单。
和「配额规则要验证它真的按写的那样跑」同族——那条说的是规则没生效，
这条说的是规则生效了、分值却不足以改变名单。
**判据：写完一条扣分规则，先去查它要挡的那几条现在多少分、扣完剩多少分，
再决定分值。**

**同一把尺子要一直用。** 「作者得真的动过手」这条毙掉过宝玉的观点文，
后来也毙掉了一篇写得不错的微软效率报告分析——后者作者自己没动手。
一致性比单篇的好坏更重要。

**收录率低于健康线，先数入围名单里「规则拦不住的那几类」占多少，再决定动不动规则。**
2026-08-06 收录率 12%、08-07 收录率 14%，连续两天低于 30%，但两天的原因相同：
推广稿 + 产品自荐 + 聚合站摘要页合计占了入围名单的 40% 上下
（08-07 是 22 条里 9 条），而**这三类没有一类是权重或反向词能拦住的**——
推广稿真的在讲用 agent 干活，自荐帖真的踩过坑，摘要页真的是 agent 主题。
`relevance.mjs` 判的是「像不像 agent 实践」，落点是评审那一步的活，两者不可互相替代。
所以收录率是**供给成分**的指标，不是规则松紧的指标。要用它调规则，
得先把「规则本来就管不着的那几类」减掉再看。

**推广稿会脱掉容易认的外衣。** 2026-08-06 掘金那波 TRAE 稿还明着挂
`#TRAE Work 实战帮` 话题标签，08-07 就不挂了，改成三条 SEO 标题
（「Cursor 平替方案有哪些」「Copilot 替代品有哪些」「团队编程效率如何提升」），
各配一行「更新日期」和「适用人群」，正文照旧是「原工具贵 → 维度对比表 →
一段一手叙事 → 基础版免费 / 国内直连」。**不变的是落点和结构，变的是标记。**
所以判据只能钉在落点上；任何基于「有没有某个标签 / 某个词」的识别都会在第二天失效。

**同一时间戳一起挂掉是管道问题——但「挂掉的那几个」里可能混着一个真死的。**
2026-08-07：东方星痕和樵夫的小站同为连续 6 次失败、同一批 503，
手动查证却是两回事——`ystyle.top` 首页 200、`atom.xml` 连 curl 三次是
reset / reset / 200；`geofftools.cn` 首页和 feed 都是连接失败，三轮全挂。
~~**分辨方法：探一下站点首页。**首页活着 = 出口抖动，首页也死 = 站点真死。~~
另外那三次 curl 只隔几秒，说明代理不是「某个时间窗口整体不通」，
而是**每一次连接独立地有概率被 reset**，feed 越大命中概率越高——
所以对付它要加**次数**，不是拉长间隔（`fetchAllSources` 已改成补两轮）。

**上面那条判别法的后半句 2026-08-08 被证伪：手动探测探不出源的死活，只有重试次数能。**
8-07 手动 curl `geofftools.cn`，首页 000、feed 000、三轮全挂，据此判「这是真死」
并建议次日到 7 天线时 `enabled: false`。8-08 它抓通了，`consecutiveFailures` 归零——
和它一起归零的还有同样连续 6 次失败的东方星痕，当轮 6 个失败源**全部**被重试救回。
**如果照昨天的建议停了它，一个活着的源就永久出局，而且错误再也无法自我纠正。**
所以：连着几十次失败也不要靠一次手动探测就下停用的结论；
「首页也挂」只能说明那一刻这个 host 整个不通，不能区分是站死了还是出口对它不通。
判死活的唯一可靠信号是**重试之后仍然失败**，而重试是免费的。

**`tinker-harvest.mjs` 有 `--index <id>`，只扫一个索引。**
2026-08-07 的 REVIEW 把「只扫新索引」列成待实现的改进，是因为按 `--only` 这个名字
搜了一遍没搜到。它一直都在（`flag('index', null)`），只是名字不同、手册里没写。
**下结论说「这个功能没有」之前先 grep 一遍 flag 解析，别按自己假定的名字搜。**
实测值得：`--index bloghub` 304 个候选 15 分钟跑完，
而全量五索引 3227 个候选估算三个多小时、日更那一轮根本等不起。

**名录之外还有第二条边：已收录博客的友链页。** 2026-08-11 第一次走通，也是连着三轮扩源
（bloghub 0、四索引第四轮 0、08-10 WebSearch 0）之后第一个非零结果。
名录问的是「有人把你收进榜单」，友链问的是「写博客的人自己认识谁」——
后者天然偏个人、偏小众、偏不上榜，正是名录系统性漏掉的那批。
207 个已收录博客 → 1521 个站外域名 → 去掉已收录和 denylist 剩 1473 个候选，
其中被 **2 个以上**已收录博主同时挂着的 208 个先跑，**11 个过评分器、人工留 6 个**。
脚本是 `scripts/tinker-blogroll.mjs`，判据直接复用 harvest 的 `evaluate()`。

**友链有传递性，但同一片圈子往外再走一步走不远。** 2026-08-11 拿并入的 14 个新源
当种子跑第二轮：207 → 221 个种子，1521 → 1640 个站外域名，**净新增候选只有 94 个，
重叠率九成以上**。原因是那 14 个种子本身就是从上一轮友链里挑出来的，
它们认识的人和挂着它们的人高度重合。
**要检验友链是不是「换个圈子还能出货」，得找一批不是从友链里来的种子**——
拿友链的产物当下一轮友链的种子，测的是圈子的直径，不是这条通道的产能。
（另：1567 个候选的 feed 探测要一个多小时，日更那一轮的时间窗放不下，只能归周更。）

**但入链数是吞吐启发式，不是质量启发式。** 同一轮里先跑了「≥2 入链」的 208 个，
理由听起来很顺——被两三个人同时挂着的更可能同频。跑完全部 1473 个才发现：
**本轮质量最高、也是创刊以来单站最高的 `qiyec.site`（14/20 够格）只被一个人挂过。**
入链数可以决定**先跑谁**，绝不能决定**跑不跑**；要分两趟就两趟都要跑完。
这是「用一个和目标相关但不等价的信号做硬截断」的通病，
和 `FORUM_SHARE` 按 kind 判、篇幅判据量整页是同一族错误。

**探上千个候选时不能用 `probeSite()`。** 它串行试十来个 feed 路径、每个 15 秒超时，
一个死站要耗三分多钟：实测跑到 96/1473 用了 25 分钟，按这个速度要六小时。
改成「首页抓一次拿 `<link rel=alternate>`，拿不到就并发试 4 条常见路径、6 秒超时」之后，
208 个候选十分钟跑完。**代价是漏掉 feed 藏在冷门路径又不声明的站**，值。
和「每加一个 harvest 索引，全量重扫的代价就线性涨一次」是同一类账。

**社区索引这条扩源路已经榨干，别再接第七个了。**
四索引连扫四轮：19 → 12 → 7 → 0（第四轮命中全是第三轮的落选者）。
2026-08-08 单扫 bloghub（另一拨人按另一套标准挑的 376 条，
和 timqian 只重叠 223、**净新增 153**，本该是最有增量的一批）：**304 个候选，0 命中。**
两个独立索引先后归零，说明缺的不是名录数量——
中文个人博客里写 agent 实践的池子就这么大，换个名录还是同一批人。
再花力气应该花在**新搜索平台**和**查询词**上，不是第七个 OPML。

**每加一个 harvest 索引，全量重扫的代价就线性涨一次。** 2026-08-07 五索引
去重后 3227 个候选，当天的网络条件下 25 分钟只走到 460，估算要三个多小时，
日更那一轮等不起，只能中途终止——**新索引 lotosbin 的命中因此一条都没审过**。
接新索引之后应该跑 `--only <新索引>` 拿一份干净的、只属于它的命中列表，
而不是每次都把前面几个索引重扫一遍。
