**这份要每次开工前完整读一遍。** 它不是流水账（那是 `REVIEW.md`），
只放已经被数据验证过、且下次还会用得上的结论：踩过的坑、走不通的死路、

## 词表与匹配

**别名的唯一标准：它单独出现时是否只可能指这个产品。** 和语言、长度都无关。
三次踩坑，一次比一次隐蔽：

| 别名 | 误命中 | 为什么规则拦不住 |
|---|---|---|
| `dia` / `amp` | ASCII diagram、example | 子串匹配，加词边界可解 |
| `&amp;` → Amp | feed 正文里的 HTML 实体 | 前后都不是拉丁字母，词边界无效，要单独排除 `&` 前缀 |
| `心流` → iFlow | 「核**心流**程」 | 中文没有词边界，两个字的别名基本都会误伤 |
| `operator` → ChatGPT Desktop | Kubernetes Operator、C++ 重载、`operator: 'eq'` | 它本身就是独立单词，任何边界规则都拦不住 |

同类嫌疑仍在表里靠打分权重压着：`comet` `crush` `goose` `continue` `jules`。
下次误判就删。

**别名还有第二种错法：不是误命中，是认错人。** 上面那张表里的每一条都是
「一个词顺带撞上了别的东西」，命中里有对有错，靠打分权重还能压一压。
2026-08-10 发现的是另一种：`workbuddy` 从创刊那天起写在 `cowork`（Claude Cowork）的
`aka` 里，而 **WorkBuddy 是腾讯 CodeBuddy 团队的桌面办公 agent**（workbuddy.cn，
文档挂在 codebuddy.cn/docs/workbuddy 下），两家公司的两个产品。
这种别名**每一次命中都是错的，一次都不对**，权重压不了，只能拆成独立词条。
症状是它一直很安静：误命中会在 `preReasons` 里留下明显不搭的组合，
而认错人看起来完全正常——「标题命中：cowork」出现在一篇讲 WorkBuddy 的稿子上，
一眼扫过去毫无破绽。**加别名时除了问「它会不会撞上别的词」，还要问
「它本身是不是别人的名字」。**

**「认错人」里最难的一种：一个产品的名字被另一个产品的名字整个包住，拆词条不够。**
2026-08-11 量到第二例：`TRAE Work`（字节的桌面办公 agent）15 条命中、14 条在标题，
全部被判成 `Trae`（它家的 IDE）——`trae` 全部 26 条标题命中里这批占了一多半，
页面上点「Trae」筛选器过半是另一个产品。和 `workbuddy` / `cowork` 是同一类错，
但那次两个名字不共一个字母，**拆开就完了；这次 `TRAE Work` 里带着 `Trae`**，
加了 `trae-work` 词条之后裸 `trae` 照样每篇都命中一次。
所以词条支持一个可选的 `not`：匹配前先把被排除的短语从文本里**抹成等长空格**再跑。
抹成等长而不是删掉——删掉会把两侧字符黏起来，破坏 `makeMatcher` 的词边界判断。
好处是它只影响被标注的那个词条：「TRAE Work vs Trae」这种同时提到两者的标题两个都命中。
**判据的第三问：除了「它会不会撞上别的词」「它本身是不是别人的名字」，
再加一句「有没有别人的名字把它整个包住」。**
（配套一条：`UNQUERYABLE` 从此不只装「太泛的名字」，也装「不泛但脏」的——
`trae-work` 名字很独特，但它的中文语料几乎全是投稿稿，主动搜等于每天往入围名单里
灌一批注定被毙的东西。**词条要加**（不然标签是错的），**查询词不要**。）

**别名的第三种错法：为了躲误伤，限定词贴得太紧，于是漏掉正常语序。**
前两种错法（误命中、认错人）都是「收多了」，这一种是「收少了」，而且**完全不报警**。
2026-08-11 一次量出三处：`worktree` 19 条只认出 4 条、`spec-driven` 14 条只认出 6 条、
`agent skills` 只写了复数、`ai coding` 整个漏在 `SOFT_TERMS` 外面。
以 worktree 为例，别名写的是 `agent worktree` / `worktree 并行`——要求限定词**紧挨着**词，
而真实标题是「多个 AI Agent 同时改一个项目，我用 git worktree 让它们互不打架」，
限定词在句子里，不在词旁边。
**查法：拿 `_raw.json` 对每个话题算「文本里出现 / 被别名认出」两个数，比值低的就是这一类。**
放宽的安全边界仍然是那条老规矩，只是要用数据而不是想象来定：
`git worktree` 命中 13 条**逐条看完全部是 agent 语境**（连唯一一条从纯 git 讲起的
「Git Worktree 实战：从多分支并行，到 AI Agent 隔离」也是），才敢收；
裸 `worktree` 那 6 条差额里有 tmux 编排和纯分支管理，仍然不收。
三字母缩写（`SDD`）也是一样：10 条命中逐条查过，没有一条是别的意思，才加。

**别名的第四种错法：判断本身没错，但词的所有权会随时间转移。**
前三种（误命中、认错人、限定词贴太紧）都是写下来那一刻就错了；这一种是**当初对、后来过期**。
2026-08-17 一次量到两处：`harness` 的注释写着「test harness / wire harness 都是常用词，
绝对不收裸词」，`skill` 写着「soft skill / skill tree 都是常用词」——
在 1350 条中文语料里，这两类反例**各 0 条**，而漏掉的是
裸 `harness` 52 条（全部 agent 语境，55 条标题里有它）、裸英文 `skill(s)` 153 条（18 条在标题）。
中文技术语料在这一年里把这两个词整个让给了 agent。
**判据：凡是「因为会撞上别的意思所以只收限定词」的别名，都要定期拿新语料复量一次
「那个别的意思还在不在」**；量法和放宽 `git worktree` 那次一样——先算「出现 / 被认出」，
再逐条看差额，反例为零才动。放宽时把「出现第一次误伤就退回去」写进注释，免得下次重查。
（附带一条边界：这次只放宽了英文写法。中文的「技能」照旧不收——招聘帖里
「技能要求」「技能包括」满地都是，而中文没有词边界。）

**反向词表也要过正向词表那三问，尤其是「它是不是某个常用词的一段」。**
`ANTI_MARKERS` 从创刊起就没按这个标准审过。2026-08-17 查出 `低价` 是**「低价值」的一段**：
18 次命中里 7 次是 `低价值`（「不允许发明低价值工作」）和 `低价团`（旅游新闻），
误杀的那篇是「AI 写了一个月代码，人类只提交 13 次」——作者把仓库拉下来数了 841 次提交、
把人类那 13 次逐条点开。而真正的黑产帖**每一条都同时命中 `中转`**，删掉 `低价` 一条不漏。
**但删之前一定要量「唯一命中数」和「删掉后会翻成入围的条目」**，光看「这个词看起来太泛」会改错：
同一轮里 `广告`（48 次命中，抽样 14 条只有 1 条真是广告）看起来更该删，
实测删掉翻进来 4 条、其中 3 条是垃圾（招聘 JD、跨境专线试用、PH 热榜），
和 08-03 量 `免费额度` 得到的是同一个结论——**看起来该删，实测它挡住的比误伤的多。**

**工具和话题是两个维度。** `TOOLS` 是产品（能安装、能打开），
`TOPICS` 是概念与实践（MCP、CLAUDE.md、Vibe Coding、规格驱动开发）。
打分时等价，页面上必须分开——混在一个叫「按工具」的筛选器里是分类错误。

**查询词从词表自动派生，不要手写。** 手写会和词表脱节：
加了工具忘了加查询，这个工具就永远搜不到。

**但「自动派生」不等于「真的被搜过」——按天平移的窗口，起点里不能带着池子长度。**
2026-08-17 查出轮转池从来没有真的轮转过：起点是 `(days * rotating) % pool.length`，
`days` 是两万多的大数，**池子每加一个词（也就是每次改词表）取模结果就跳到不相干的位置**，
于是「每天平移 24 格」变成「每改一次词表就随机重开一次」。
13 天 312 个查询槽只碰到 254 个词里的 145 个，**尾部 61 个（24%）一次都没跑过**，
其中包括全部 TOPICS 派生词。症状是按词表位置画出来的轮次是一个
**中间 4 轮、两头 0 轮的平滑驼峰**——又一次「分布过于整齐时先怀疑管道」。
改法是让「什么时候轮到你」和池子长度脱钩：`cycle = ceil(池子 / 每日额度)`，
第 i 个词属于第 `i % cycle` 桶，当天跑第 `days % cycle` 桶；
性质是每个词每 cycle 天恰好跑一次，中间插词只让后面的人各挪一个桶。
**两条推论**：(1) 这个 bug 同时废掉了 `query-yield.json`——账本永远攒不够轮次，
「换掉长期零产出的查询词」这条手册指令在修好之前根本执行不了，
**发现某个账本长期攒不够数据时，先怀疑写账本的那条路径而不是数据太少**；
(2) 原有的覆盖测试是通过的，因为它拿一个**不变的**池子跑 14 天——
**测演化中的行为要在测试里让输入本身变**（现在那条测试每两天往池子中间插一个词）。

## 信源

**博客不供货，搜索源供货。** 2026-08-02 实测：新增 51 个博客源
→ 23 条原始条目 → **0 条入围**；同一天 6 条入围全部来自搜索源。
中文个人博客写 agent 实践的池子是真的薄，不是挖得不够。
**别再把「加博客数量」当提高供给的手段**，力气花在查询词和新搜索平台上。

**「抓取失败」先分清是站点失败还是出口失败。** 2026-08-06：当天 7 个失败源
全是 `HTTP 503`，查下来 **6 个其实是活的**——503 来自本环境的出口代理，
响应体只有 48 字节，带 `x-deny-reason: resolve_failed`，正文写着
"DNS resolution failed (transient resolver error)"，**代理自己说了这是 transient**；
另一种是上游 TLS 被 reset。而 `get()` 只把 `res.status` 拼成 `HTTP 503` 抛出去，
上层分不清「站点死了」和「出口抖了一下」，一律计进 `consecutiveFailures`。
危险的不是少抓一天（那 6 个当天本来也没新文），是**源的死活判断建在被污染的计数上**：
SkyWT / 东方星痕已经连续 5 天记为失败，再过两天就会被按噪声停用，
而停用之后它们再也不会被抓，错误无法自我纠正。
现在抓取失败会重试一轮（`fetchAllSources()`，网络类失败才重试，404/403 不重试），
两轮都没拿到才记 failure。
**推论：一批源在同一时间戳一起挂掉，几乎一定是管道问题而不是托管商问题**——
8-01 那批「像是同一家托管挂了」的源，其实就是那一轮出口 DNS 抖了。

**搜索引擎发现不了博客，但发现得了「博客的名录」。** 这是对下面那条的补充，不是推翻。
2026-08-06 第七次验证「搜个人博客只出 SEO 平台页」之后换了个搜法：
不搜「XX 踩坑 博客」，改搜索引本身（`OPML` / `订阅列表` / `博客榜` / `feeds list`），
返回的立刻全是索引仓库。第五个索引 lotosbin/opml-list（1328 条 feed）就是这么找到的，
待接的 qianguyihao/blog-list（605 站，明确「不接受自荐」）也是。
**扩源缺的一直不是博客，是名录；按名录搜就有，按博客搜就没有。**

**找新博客只走社区索引，别走搜索引擎。** 三次同样的结果，别再试第四次：
搜索引擎返回的是 SEO 平台页和文档镜像站（opencodecn / learnopencode / claudecn 这类），
个人博客根本排不上去。2026-08-03 同一轮里做过直接对照——
4 组 WebSearch 探到 4 个候选站，逐个查完**一个都不够格**；
同一轮 `tinker-harvest.mjs` 扫 2986 个 feed，命中 19 个，人工过滤后并入 3 个。
搜索引擎的正确用途是**查证某个具体站点**（抽一篇看是不是转述文档），不是发现站点。

**harvest 会静默跑很久，不要按「多久没出字」判断它死没死。**
2986 个 feed 实测约 35 分钟，且进度全缓冲到结束时一次性吐出，
中途 `wc -c` 输出文件一直是 0 字节。踩过一次：以为它挂了，先按「本轮没并入新源」
收了尾，结果它带着 19 个命中正常退出。

**「这个源零命中」之前先量它的采样窗口有多宽。** 2026-08-11 查清死源时，
NodeSeek 是全库唯一一个「21 天 20 条、命中 agent 词表 0 条、入围 0、收录 0」的高量源，
看起来是标准的该停用对象。查下去发现 **它的 `rss.xml` 只给最新 20 条，而这 20 条跨度
21 分钟**——交易区和日常区发帖太快，一天抓一次等于每天只看 1440 分钟里的 21 分钟，
而且看到的永远是那一刻交易区在干什么。21 天 20 条这个数字本身就是「每天采到一次」的结果。
它的 channel 里明明白白列着 `tech` / `dev` 分类，只是我们从来没采到过。
（找过分类入口：`/categories/tech`、`rss.nodeseek.com/?category=tech` 等六种写法，
本环境下不是 403 就是被忽略，没有可用的窄入口。）
**推论：判一个源「不写这个主题」之前，先看它 20 条覆盖多少时间。
覆盖几个月 = 真的不写；覆盖几十分钟 = 你只是没看见。**

**同一个病，iThome 有药：窄窗口的解法是接子 feed，不是想办法把全站 feed 撑大。**
2026-08-13 量到第二例：`ithelp.ithome.com.tw/rss/articles` 固定 20 条，
铁人赛赛季里这 20 条只跨 **327 分钟**——每天只看得见清晨五个多小时发的东西。
分页参数（`?page=2` / `?limit=100`）**全部被忽略**，返回和第一页一字不差，
所以扩窗口这条路是死的；但 `rss/series/<id>` 通，一个系列 30 条全给。
和 NodeSeek 的区别就在这里：那边找遍六种写法没有可用的窄入口，这边有。
**先花五分钟试窄入口，再决定是接受采样还是放弃这个源。**

**扩源的第三条通道：赛事 / 活动的报名表。** 前两条是社区名录（已榨干）
和已收录博客的友链页。2026-08-13 走通第三条：iThome 铁人赛的报名列表
`/2026ironman/signup/list?group=<组>` 按组列出全部参赛系列，
2026 年有 `claude-ai` / `chatgpt-and-codex` / `vibe-coding` / `ai-engineering`
等七个 AI 相关组，每个系列一条独立 feed。
和名录、友链问的问题都不同：名录问「谁被收进榜单」，友链问「写博客的人认识谁」，
报名表问的是**「谁正在为期 30 天地写同一件事」**——供给密度天然高，
而且报名时就按主题分好了组。
30 个系列 191 篇实测：够格的 2 个系列（5/13 和 2/5），一次并入两个源。
**两条配套的坑**：(1) 不能用 harvest 的 `evaluate()` 判准入——它带一条
「近 20 篇跨度 ≥14 天否则像媒体」的闸，而赛制就是日更 30 天，
所有参赛系列一律不合格；判据换成「近 20 篇里几篇过 `scoreItem()` 的入围线」。
(2) 这条通道有季节性（每年 8-9 月），系列停更后按常规留存标准自然沉底即可。

**列表页通道走通之后，第一件事是确认它有没有分页。** 2026-08-13 接铁人赛报名表时
按 `signup/list?group=<组>` 抓，每组返回 10 个系列，就当成「这个组一共 10 个」；
2026-08-17 翻第 2、3 页，四个 AI 组又多出 **28 个系列、120 篇**（第一页那 40 个系列是 387 篇）。
**第一页的产量不是这条通道的产量**，而漏掉的那批不会以任何形式报警。

**友链这条通道是简中博客圈的方言，繁中圈没有。** 2026-08-17 拿 11 个繁中源
（ihower / Huli / 黑暗執行緒 / israynotarray / Kalan / MinglunWu / 電腦玩物 /
Ruyut / raven.tw / imzlp / keggin）当种子跑 `tinker-blogroll.mjs`，
**只爬出 9 个站外域名，其中 8 个来自唯一一个简中风格的博主**。
逐站查过：那几个站首页全部 200、链接几十上百条，**没有一个页面是友链页**；
ruyut 的「友站」指向 404，israynotarray 和 電腦玩物 的 `Links` 页是社交账号和自家电子报。
「友情链接」是 Hexo / Hugo 那几套主题带起来的简中约定，别再拿它去挖台港。
（顺带：那次发现 `LINK_ANCHOR` 只有简体写法，和 `SELF_PROMO` 在繁体语料上从没命中过
是同一个洞——**每加一个新字形的源，回头把所有中文正则查一遍**。）

**扩源的第四条通道：另一种语言的写作平台。** 前三条是社区名录（已榨干）、
已收录博客的友链页、赛事报名表。2026-08-15 走通第四条：**方格子 vocus**
（台湾最大的中文写作平台）。它和前三条问的问题又不同——名录问「谁被收进榜单」，
友链问「写博客的人认识谁」，报名表问「谁正在为期 30 天地写同一件事」，
写作平台问的是**「另一片互联网上，不写博客的人把文章发在哪」**。
产能实测（各标签近 15 条按 `scoreItem()` 打分）：`Codex` 9/15、`Cursor` 3/15、
`ClaudeCode` 3/15、`OpenClaw` 2/15。和 iT 邦幫忙不重叠：那边是工程师写给工程师，
这边混着非工程师用 agent 干活的记录。
配套的三条经验：

1. **拿不到搜索接口时，先翻一遍页面自己在调什么。** vocus 的 `/api/search?q=`
   恒返回空数组、网页 `/search` 直接 404，看起来是死路；而 tag 页的
   `__NEXT_DATA__` 里躺着 SWR 的 fallback key，写明了真实接口
   `api.vocus.cc/api/contents?tag=&sort=publishAt&order=desc`。
   **「客户端渲染」是页面的性质，不是接口的性质**——博客园 zzk 那条结论
   （见死路表）说的是那个站没有可用接口，不能推广成「凡是 SPA 都放弃」。
2. **排序参数仍然是硬门槛。** 接口支持 `sort=publishAt&order=desc` 才敢接，
   理由和掘金 `sort_type=1`、B 站专栏那两条完全一样。
3. **标签是用户手打的，同一个产品有多种写法。** vocus 上 `Claude Code` 只有 4 条，
   而 `ClaudeCode` 有 15 条。接标签型平台时，带空格的名字要连紧凑写法一起发。

**但第四条通道不叫「写作平台」，叫「以中文为母语的写作平台」——标签的命名空间是谁的，
决定了这条路通不通。** 2026-08-16 顺着同一个思路试 Medium 的 tag feed，
`medium.com/feed/tag/<tag>` 通、HTTP 200、按时间排序（排序那道硬门槛过了），
看起来和 vocus 是同一个形状。实测五个标签 48 条：**中文只有 5 条，按 `scoreItem()`
够格 0 条**；而且 `claude-code` 这种热标签 10 条只跨 **5 小时**
（NodeSeek / iThome 那个窄窗口问题，分页参数无解，扩不开）。
区别不在平台大小，在**中文作者在那里是少数派，挤在英文的标签底下**——
`claude-code` 这个标签是英文世界的，中文实践文只能碰运气混进那 10 条里；
vocus 的 `ClaudeCode` 标签下则全是中文。
**评估一个标签型平台时，先问它的标签命名空间是不是中文的，再去测产能。**

**扩源的第五条通道，也是最便宜的一条：今天收的这篇，作者自己有没有站。**
前四条是社区名录（已榨干）、已收录博客的友链页、赛事报名表、以中文为母语的写作平台。
第五条 2026-08-18 走通：当天收的 V2EX 那篇「161 个 Claude Code 会话成本审计」，
作者 kuhung 有个人博客，`evaluate()` 判 6/20 够格、span 95 天，按严标准直接准入。
它问的问题和前四条都不同——名录问「谁被收进榜单」，友链问「写博客的人认识谁」，
报名表问「谁正在为期 30 天地写同一件事」，**这条问的是「已经被我们判为好文的那个人，
是不是还在别处写」**。原料每天免费送上门（搜索源的收录条目里本来就带作者名），
命中率也高得多：当天只探了 4 个候选就中 1 个，而名录一轮 1473 个候选才留 6 个。
**配套的坑：探到首页 feed 不等于探到文章 feed。** kuhung.me 的 `index.xml` 里
只有「关于我 / 内容精选 / 归档」三个页面，看起来像个只有 4 条的死站；
真正的正文 feed 是 `posts/index.xml`（157 条）。Hugo 这类静态站按 section 分 feed，
`probeSite()` 命中根 feed 就停了。**判一个候选站「量太小」之前，先试一次 `/posts/index.xml`。**

**第五条通道有个不用猜的入口：平台的 profile 接口。** 2026-08-19 补的。
V2EX 的 `https://www.v2ex.com/api/members/show.json?username=<name>` 公开可调，
直接给 `website` / `github` / `bio` 三个字段——当天新接的 php.js.cn 就是这么拿到的
（08-18 收的那篇 DSH 服务器部署实录作者 longbill，`website` 写着 `http://php.js.cn`）。
对照着看代价：上一轮按域名猜写进 `candidates.txt` 的 `longbill.cn` 探不出任何东西，
而真正的站和用户名一点关系都没有。**作者的站不要按用户名猜，去问平台自己的接口。**
（掘金 / SegmentFault 的作者页也有个人主页字段，只是还没试过接口。）

**profile 接口这条入口不是 V2EX 独有的，掘金也有，但参数会骗你。**
2026-08-20 在掘金复现成功：`https://api.juejin.cn/user_api/v1/user/get?user_id=<id>`
公开可调，返回体里有 `blog_address` 和 `github_nickname`。
**坑在于 `aid=2608`**——掘金的搜索接口必须带这个参数，而同一域名下的用户接口
**带上它就返回 `data: null`**，看起来像「这个接口废了」，去掉才有数据。
`user_id` 从搜索接口的 `author_user_info` 里拿，不用另外查。
产能：拿最近 14 天收录条目里的 13 个掘金作者跑一遍，11 个查到 profile、2 个填了个人域名
（第三个填的是 CSDN 主页，不算），并入 1 个（i-study-everyday.online，近 10 篇 8 篇过收录线）。
**一个接口返回空之前，先把「必带参数」逐个去掉试一遍，同一个站的不同接口不共用参数约定。**

**但这条通道有个必然的副作用：新接的源和已收录条目天然重叠，`seen.json` 挡不住。**
2026-08-19 量到两例：Kuhung 的《如何最大化 Claude Code Session 的价值》08-18 刚从
V2EX 的转帖收过，当天他的个人站接进来，同一篇又以 kuhung.me 的 URL 占了一个入围席位；
掘金那篇《烧了 6B+ token…AGENTS.md》则是 08-06 从 V2EX 收的同一篇。
**这不是偶发，是这条通道的定义决定的**——它挑源的依据就是「这个作者已经被我们判为好文」。
`seen.json` 按 id/url 去重，两个 URL 不同，结构上无效。
现在 `triage()` 收一个 `publishedTitles`，标题归一化后**严格同题**的判为转帖，
照常打分留在 `rejected` 里，只是不占席位。
判据故意不用相似度：机械去重那条死路（见下）说的是「同题材的烂文 vs 同工具的好文」分不开，
而这里要分的是**同一篇**，同一篇的标题逐字相同，用不着相似度。
实测 513 条命中 2 条、0 误伤。

**凡是「查过就不再查」的账本，都必须把「查过了，没有」和「没查成」分开记。**
2026-08-21 把「已收录作者的个人站」这条通道写成脚本（`scripts/tinker-authorsites.mjs`）
并给它一份要提交的账本 `tinker/author-sites.json`。第一版没分这两件事：
出口代理那一轮在吐 `HTTP 503 DNS resolution failed`（见上面「站点失败 vs 出口失败」），
于是 20 个掘金作者全被记成「没有个人站」——而账本的用途恰恰是**以后不再查他们**，
错误会永久留在里面且再也没有机会自我纠正。现在网络失败重试两轮，
仍然失败就跳过、不写账本，等下一轮重查。
**判据：任何一份「记下来省得下次再做」的账，写之前先问一句
「这一条记的是结论，还是记的是一次失败」。**

**准入标准和留存标准必须分开。** 严标准只用在门口。
用严标准回审已有源时发现：45 个「不够格」的源里有 3 个当天各贡献了一篇已发布文章，
其中一篇是 5 分精选。一个月更博主一年出一篇好文，留着它每天只多一次 HTTP 请求。
已有源只按「连续 30 天零入选**且** feed 中期文章完全不沾 agent」清理。

**但这条判据的时钟该走出刊量，不是日历天数。** 「30 天」保护的是月更博主——
他一个月出 1 篇，凭 1 篇下结论确实太早；可同一句话对日更博主意味着 30 篇。
2026-08-17 停用 Mobius 时改的：它 21 天出 10 篇，**10 篇全是文学随笔**
（「中式番茄炒鸡蛋吃多了也会腻」「当一只章鱼在一间全是镜子的房间会如何理解自己？」），
命中 agent 词表 0、入围 0、收录 0，而 `desc` 写的是「中文个人博客，更新勤」——
当初大概只看了更新频率。判据改成：**连续 30 天零入选，或已见过 ≥10 篇且这些篇目
完全不沾 agent 词表，两者取先到。** 月更博主一年也攒不够 10 篇，照样受保护。
这和 NodeSeek 那条是同一个道理的正反两面：那次是「20 条只跨 21 分钟 = 你没看见」，
这次是「10 篇覆盖它完整的 21 天产出 = 已经看够了」。

**选源判据要用系统自己的评分器**，不要另立一套近似标准。
旧判据「近 20 篇里几篇提到 agent」是好的相关性过滤、糟糕的质量过滤——
从「订阅数最多」榜单捞出来的全是 36氪、钛媒体、爱范儿这类媒体，
它们每天报道 AI，轻松达标。加一道发文节奏闸（近 20 篇跨度 ≥14 天）区分个人博客与媒体。

**「独立博客」不等于「个人折腾」。** 有的独立域名上跑的是内容农场的形状——
标题清一色「5 个高阶技巧，90% 的开发者不知道」「30 个核心概念」「20 个你可能不知道的用法」。
判据还是落点：是在讲自己踩了什么，还是在凑一个能被搜索到的清单。

**否决理由写进 `denylist.json`，写在 REVIEW 里不算数。** 2026-08-03 的日更轮在 REVIEW
里否掉了胡涂说、api.xgo.ing、hacpai.com 三个源，但没往 denylist 落盘；同一天的周更体检
跑 harvest，这三个原样又被提名了一遍，7 个命中里占 3 个。
LESSONS 早就写着「否则每次扩源都会重新提名」，踩的仍是这一脚——
因为「记下来」和「记到机器会读的地方」是两件事。

**「写完 REVIEW 顺手落 denylist」不是一条能靠记性执行的规矩——它已经被漏掉三次。**
2026-08-05 第三次：昨天 harvest 否掉的 6 个站今天原样又被提名，7 个命中里占了 7 个，
**新源 0**。而昨天写 REVIEW 时，我就在同一份文档里重申了「写在 REVIEW 里不算数」这条。
**否决和落盘必须是同一个动作**：翻 harvest 命中列表时，否掉一个就立刻写进
`denylist.json`，不要等写复盘时补。

**但 harvest 的边际产出不只跟索引走，也跟词表走。** 2026-08-17 第五次全量扫
（3337 个候选，同样六个索引）命中 4 个，并入 1 个——不是索引变了，是
`dsh` / `pi` / `cordis` / `harness` 这些词条 8 月才进表，同一批 feed 因此重新够格。
**词表大改之后重扫一次是有价值的，扫之前不必先说服自己「肯定是零」。**

**harvest 的边际产出：19 → 12 → 7 → 0。** 同样四个索引（timqian / blogcn /
top-rss / awesome-rss，2986 个 feed）连扫四次，第四次的 7 个命中**全部**是
第三次的落选者。这四个索引可以认为已经榨干；落盘 denylist 之后若下一轮命中 0，
就是硬证据——**别再跑同样的 harvest，去找第五个索引或换发现渠道。**

**而记到机器会读的地方还不够，得记成机器真的匹配得上的形状。**
2026-08-04 api.xgo.ing 第三次被提名：denylist 按完整 feed URL 精确匹配，
而它是个 RSS 网关，每个用户一条 `/rss/user/<hash>`，同一个站能生成无限条
互不相同的 URL。现在否决按**域名**生效；例外是 wechat2rss 这种一个域名下
挂几百个互不相干公众号的聚合网关，用 `scope: "feed"` 标出来单独放行。
**加任何黑名单前先问：被否的那个东西，下次会以同一个字符串出现吗？**

**「部分查询失败」长期稳定在某个比例，先怀疑限流，别当成站点抽风。**
小众软件论坛搜索「30 个查询挂 15 个」从创刊起天天写进 REVIEW 的抓取失败里，
每次都被记成「老问题，长期如此」——2026-08-11 实测下来是 **Discourse 的匿名搜索限流**：
按 400ms 间隔连发 30 个，第 8 个前后开始一律 `HTTP 429`（响应体是中文的
「您执行此操作的次数过多」，**没有 Retry-After 头**可依），当轮 23 个全废。
诊断很便宜：8 个一轮全过、30 个一轮挂 23 个，**失败数随批量大小走而不是随时间走**，
这就是限流的指纹。修法是给源加 `maxQueries`（appinn 设 8）按额度截断，
不是退避重试——限流窗口按分钟计，而这个源近 10 天收录数是 0，
不值得为它给日更管线加几分钟等待。
**顺带一条通用的**：截断之后「整源失败」的分母必须换成**实际发出的条数**，
否则 8 发 8 挂会被算成「8/30 部分失败」混过去。

**平台搜索必须显式按时间排序，默认排序会安静地废掉整批查询词。**
掘金原来用 `sort_type=0`（综合），返回的是历史高热文章：2026-08-03 实测
「Claude Code 踩坑」20 条结果里 **21 天窗口内 0 条**，最新一条是 6-19；
换成 `sort_type=1`（最新）后同一个词 20 条里 18 条在窗口内，最新就是当天。
症状极具迷惑性：当轮 30 个查询里 23 个零产出，而零产出的**全部**是词表派生词、
6 个核心词全部有货。看起来像「长尾词没人写」，实际是核心词热度够高、
连几个月前的老文章里也混得进新的，把排序问题伪装成了选词问题。
**分布过于整齐（恰好沿着某条分类线切开）时，先怀疑管道而不是内容。**
V2EX 用 `sort=created`、Discourse 用 `after:`，加新搜索源时第一件事就是确认排序参数。

**自动命中必须人工过一遍再合。** 有两类源机器判不出来，都只能靠人扫一眼：

1. **大厂官方技术号**（腾讯技术工程、小米技术、字节跳动技术团队，通过 wechat2rss 进来）
   写的文章确实像实践文，`scoreItem()` 拦不住，但它们正是要排除的「官方和正式的东西」。
   **注意这一条的适用范围是「源准入」，不是「单篇」。** 2026-08-12 划清楚的：
   一个 feed 里绝大多数是公司稿，接进来等于每天往名单里灌一批注定被毙的东西
   （和 `trae-work` 加词条但不派生查询词同理），所以整类不接。
   但**从搜索源单篇进来的，仍按落点和一手性判，判据是「这篇在推谁」而不是「发在谁的号上」**。
   当天收的百度Geek说那条多仓库 worktree 就是：讲他们自己踩的并发坑
   （两个 Agent 会话同时算出同一个 REQ-ID）、给的解法可复用（用 git「同名分支建不出
   第二次」当互斥）、还主动写明只在单机成立，一句产品都没推，前作挂在作者本人博客上。
   反过来如果通篇在讲「用我们的 X 平台一句话交付需求」，同一把尺子照样毙。
2. **翻译站**。2026-08-08 的 Teach Talk（ttalk.im）差点收了：标题清一色
   「通过工程化的 Harness 改进 Deep Agent」「构建 Claude Code 的经验教训：
   Prompt 缓存就是一切」「不要再构建多 Agent 了」，选题对口到不像话，
   `scoreItem()` 给了 2/20 够格。抓一篇一看，正文是英文原文的中译，
   文末规规矩矩标着出处，本人补充只有一段译者评注。
   **判据：选题密度高得反常的中文站，先抽一篇看文末有没有「原文：」。**
   要发布的单位是文章，而文章是译文——译者评注再好也救不回来。

3. **开源产品的官网博客**。2026-08-11 友链页扫出 `halo.run`（Halo CMS 官网），
   `scoreItem()` 判 2/20 够格。它不是大厂，但形状一样：「Halo 和 WordPress / Ghost /
   Hexo / Hugo / Strapi 对比」成套 SEO 稿 + 建站科普。**判据：产品方在写自己的产品。**

否决过的记进 `denylist.json`，否则每次扩源都会重新提名。

## 筛选规则

**规则的适用范围会随系统演化而失效，而规则本身看起来仍然合理。**
`FORUM_SHARE`（论坛占比封顶）从写下到失效只隔了几小时——
期间供给结构从「博客为主」变成「搜索源为主」，
而我按 `kind in {forum, search}` 判定，把「怎么抓」当成了「抓到什么」。
掘金搜索和 V2EX 搜索的 kind 都是 `search`，但前者返回文章、后者返回论坛帖。
后果是当轮 7 条入围、**21 条被这条规则挡掉**。
现在按信源上显式的 `thread: true` 判定。
**以后每加一条基于当下数据分布的规则，都要写清它依赖什么前提。**

**但发现「这条规则量的是怎么发」之后，别急着把罚分调小——先造语料量一遍。**
2026-08-13 是这个形状的第四例，也是**第一例「按老剧本改会改错」**。
`SERIAL_TITLE`（连载章节体标题 -4 分）在 iT 邦幫忙撞上铁人赛：
8-9 月赛季里那个平台上**所有**连载都必须叫 `Day N`，包括真折腾，
所以这条规则在这个平台上量的确实是「怎么发」。前三例（`FORUM_SHARE`、
V2EX 首帖篇幅、thin 席位）的结论都是「别按它扣分」，照抄就该减罚分。
**照抄会错。** 把 2026 铁人赛三个 AI 组共 30 个系列、191 篇正文拉下来重放：
罚 4 分够格 3 篇，罚 1 分够格 18 篇，多出来的 15 篇**逐条看完全部是教学连载**
（「認識 ChatGPT 與 Codex：AI 開發新搭檔」「什麼是Vibe Coding？」
「打造AI開發環境：Cursor / VS Code + AI插件最佳設定」）。
也就是说在这个平台上「Day N」和教程内容**确实**强相关，原判据只是不完备。
真正能分开两者的是**正文经验词密度**：那 15 篇是 1-3 个，
被误杀的那篇实录（「我的 AI 沒有資料庫：全 Markdown 架構」）是 4 个。
改法是**条件式罚分**——正文经验词 ≥4 时罚 2，否则照旧罚 4；
同一份 191 篇样本重放，够格数仍是 3，误杀那篇 5 → 7 进了名单。
**通用判据：放宽一条规则之前，造一份「这条规则的目标语料」（不是当天那 20 条）
去量各个档位的产出，再决定放宽哪个维度。凭直觉调数字会在正确的诊断上做错的手术。**
（2026-08-17 用 68 个系列 507 篇的**完整正文**复量了一次，结论不变：
阈值放宽到 ≥3 多进 5 篇、≥2 多进 9 篇，**全部是教学连载**。造这份语料时注意
RSS 描述只有 92 字符，用它量「正文经验词密度」等于量了个寂寞，必须逐篇抓页面
并用 `tinker-fetch` 同一个 `extractArticleText`。）

**规则层结构性看不见的一类作者：写结论、不写产品名。** 2026-08-17 复量铁人赛 9177
《一個人的 AI 團隊：Claude Code 當組長》，10 篇 **0 篇够格**、最高 3 分，
而标题是「中文亂碼是三種不同的病，先分流再治」「它回話了，不代表它做完了」
「能力會漂移，所以要有一張煞車燈」——人读起来明显好过分数。
病因不是 `SERIAL_TITLE`（罚分归零后最高的一篇也才压线 6 分），
是**工具名一次都没出现在标题上**，全靠正文命中拿 1-2 分，而标题命中值 6 分。
不要为这类作者放宽标题命中的权重——那会把一整片泛 AI 内容放进来。
**该记住的是结论本身：这类源即使收进来，它每天也只会落选**，
所以判「不收」的理由要写成「规则看不见它」，而不是「它分数低」。

**论坛帖的「篇幅」必须量首帖，量整页等于把导航和回复算成作者写的东西。**
`relevance.mjs` 的「论坛短帖 <600 字符扣 3 分」写得没错，但它在 V2EX 上
**从来没有量到过正确的字符串**。2026-08-09 实测三条入围帖：「codex 20260808 重置了」
首帖 0 字符、「所以买 codex pro 是没有意义的吗」0 字符、「Codex for oss…求支招」17 字符
（V2EX 首帖为空时页面里连 `topic_content` 这个 div 都不生成），
而它们的 excerpt 分别是 711 / 1305 / 793——页面固定 chrome 就三百多字符，
回复区再垫几百，任何一个纯标题帖都能凑过 600，还能从别人的回复里白捡
「正文经验词 3 个」的加分。三条各占了一个评审席位。
成因：`needsEnrich` 那条「thread 且 feed 已给内容就不补全」只保护得住 Discourse
（RSS 里就是首帖全文）；V2EX 的 tech.xml 给空内容，于是走补全，补回来的是整页。
**规则本身合理，喂给它的输入却来自「怎么抓」而不是「抓到什么」——和 `FORUM_SHARE`
那次是同一个形状。加任何基于长度 / 篇幅的判据前，先确认量的是不是作者写的那段。**
现在 `threadBodyHtml()` 三态返回：切得到首帖给 HTML，切不到给 `''`（确认为空，
不许拿整页顶上），没有切法的站给 `null` 走原路。

**「落点在结尾」的判据，必须确认你手里那段字符串真的是结尾。**
2026-08-20 量到的第三例「规则合理但输入由怎么抓决定」（前两例是 `FORUM_SHARE` 按 kind 判、
论坛篇幅量整页）。`SELF_PROMO` 的结尾分支看的是 `excerpt.slice(-400)`，
而 `excerpt` 是 `extractArticleText(html, 2500)` 的产物——**正文一旦超过 2500 字符，
那 400 个字符就是正文的腰**。当天 36 个入围条目里 19 条（53%）被截断，
这条判据对它们从上线起就没生效过，而自荐帖的招呼语恰恰压在最后一段
（「MIT 协议开源，欢迎 star」「以上文章均可在我的个人博客找到」「新用户 300 万免费 token」）。
现在抓取层单独带回 `tail`（正文最后 400 字符，没截断时为空串），判据用 `tail || excerpt.slice(-400)`。
**通用判据：任何按位置取样的规则（开头 N 字、结尾 N 字、首帖、前 20 篇），
都要先问一句「我取的这一段，是不是我以为的那一段」——截断、分页、页面 chrome 都会让它错位，
而且一律不报警。**
配套的一半同样重要：管道修好之后**词表往往还没跟上**。同一天把 19 条的真结尾逐条打出来，
按现行词表分数一条都没变，因为表里只有「求 star」没有「欢迎 star」。
**修完取样口径要立刻拿新样本重量一次词表，否则修的是一条仍然扣不到人的规则。**

**源出问题和「这个源的某类帖子出问题」要分开。** 承上：8-09 那天 V2EX 5 条入围全废，
但账是这么算的——创刊以来收录 64 篇里 V2EX 占 13 篇，最近 7 天有 5 天各出 1 篇、
其中 3 篇 5 分。要动的是「纯标题帖也能进名单」，不是这个源。
和 BestBlogs 那条对照着看：那条是**整源结构上永远不会有**（摘要页），所以整源降级；
这条是**一个源里的一类帖子**，所以修判据。判据：问「这个源明天还可能出好东西吗」。

**机械去重分不开「同题材的烂文」和「同工具的好文」。** 已调查，别重试：

| 方法 | 真重复组内最低 | 无关文章最高 | 可分离 |
|---|---|---|---|
| 标题二元组 Jaccard | 0.22 | **0.30** | ✗ |
| 剥掉工具名后比标题 | 0.05 | 0.15 | ✗ |
| 正文二元组 Jaccard | **0.03** | 0.40 | ✗ |

三种方法里真重复的相似度都低于真正不同的文章——因为它们不是复制，
是同一个 SEO 选题的独立改写。代码已删。同选题只留一篇，靠人读。

**配额规则要验证它真的按写的那样跑，别只读代码看它「像是对的」。**
`FORUM_SHARE` 和 `PER_SOURCE_QUOTA` 两条都写得很清楚、注释详尽、有测试，
但 2026-08-04 之前从来没有在真实数据上同时生效过：
论坛席位取的是「文章填完 cap 之后的余量」，文章型源自己够 60 条那天恒为 0
（59 条文章时论坛能拿 39 席，60 条时归零——断崖式跳变是这类 bug 的指纹）；
`byQuota()` 的补位轮不再读 `used`，按源配额对高产源等于不存在。
后果是当天分数最高的一条被判「已达占比上限」，而掘金一家吃下 45/60 席。
**已有的测试全都通过**——它们测的是规则的意图，不是规则在真实分布下的行为。
每条配额规则至少要有一条测试模拟「某一类供给压倒性多」的极端分布。

**席位的期望产出不同时，该调的是分配不是分数。** 2026-08-10 把创刊以来每天的
`_pending.json` 和当天日文件对了一遍：`thin: true`（补全失败、只剩标题）的席位
54 个换回 2 条收录（3.7%），非 thin 的 148 个换回 31 条（21%）；
而那 2 条还是编辑手动重抓正文之后才收的，不是靠标题收的。
一个 thin 席位值普通席位的六分之一，却吃掉同样的评审预算。
但**不能给 thin 扣分**——thin 是补全被限流的结果，是「怎么抓」不是「抓到什么」，
按它扣分就是第三次踩 `FORUM_SHARE` / V2EX 首帖那一脚。
所以分数一分不动，只封名额（`THIN_SHARE = 0.25`，`THIN_FLOOR = 3`），
和 `summaryPage` 同一个层次。名额要切在**配额分配之前**，
腾出来的席位才能让原本被单源配额挤掉的能读条目补进来。
地板不设 0 的理由和 summaryPage 正相反：摘要页是结构上永远不会有，
thin 是偶发的管道故障，明天可能就通了；且 8-05 那两条 thin 收录在 thin 内部分数排前二，
按分数留前几席一条都不会丢。

**入围名单是评审预算，不是必须填满的额度。** 修上面那两条的代价是
名单在「只有一个源有货」的日子会变短（2026-08-04：60 → 36）。这是要的结果：
36 条干净候选比 60 条里混 29 条内容农场文更好评。
遇到「改了规则名单变短」时不要回头放宽，先看短掉的是什么。

**不要为了「名单成分好看」不断加配额规则。** 入围名单只是给评审用的候选池，
真正的过滤在编辑那一步。某个源占得多，只要评审挑得散就没问题；
而如果那天只有它有货，砍掉反而更糟。这是这个项目里反复出现的诱惑。

## 抓取与正文

**去标签不能用 `/<[^>]+>/g`。** 属性值里合法出现 `>` 时它会在标签中途收尾，
把标签后半截当正文吐出来。真实例子是 Discourse 的响应式样式表
`<link media="(width >= 40rem)" ...>`，一个页面几十条这种碎片，
导致 linux.do 的中文帖被判「中文占比 1%」全部毙掉。
同一个正则反向也错：正文里的 `1 < 2 且 3 > 2` 会被吃成 `1 2`。
现在按标签内引号状态扫描，只认引号外的 `>`；一直没闭合的 `<` 当普通字符放回。

**实体转义过的 HTML 解码后要再去一次标签。** 有的 feed 把整段 HTML 转义后塞进
description（BestBlogs.dev 就是），解实体是在去标签之后做的，
于是每条摘要开头都是一大段 CSS。第二遍必须**不再解实体**，
否则 `&amp;lt;` 会被解两层变成 `<`（正确结果是 `&lt;`）；
用「解码结果里出现闭合标签」作为触发条件。

这两条都在共用的 `lib/html-text.mjs` 里，**信源罗盘也受影响**，改动要跑全量测试。

**补全失败不都是反爬，很大一部分是限流，隔一会儿再要就给。**
2026-08-05：16 条掘金入围条目全部 `thin`，而 thin 在评审那一步是**一律不许收**的，
等于最大供给源在评审之前就已经失去收录资格。查下来掘金返回的不是 JS 挑战页，
是 `HTTP 200 + x-tt-system-error: 3` 的 2397 字节错误页——Googlebot / curl /
完整 Chrome 三种 UA 拿到的字节数**一模一样**，和身份无关。隔几分钟按 4 秒间隔重放，
9 条拿到完整正文，其中 2 条当天收录（当天收录量的 40%）。
**但重试要克制**：紧接着按 3.5 秒、9 秒又跑两遍，两遍都是 0 收获，限流被打得更死。
现在是「等 60 秒补一轮、并发减半」，不是「重试到成功」。
判据：**返回体字节数在不同 UA 下完全相同 = 服务端状态问题，值得重试；
字节数随 UA 变 = 反爬，重试没用。**

**限流类故障的恢复是概率性的，别拿「连着几天零产出」判它永远不会有产出。**
掘金正文补全的第二轮重试在 08-08 / 09 / 10 连续三天 `enrichRetried: 0`，
08-10 的复盘写了「明天如果还是 0 就改触发条件或直接停掉」；
**08-11 它救回 5 条**（211 条重试）。这和 08-08「首页也挂 = 站点真死」被证伪是同一种错：
拿几次观测去给一个概率性的东西下确定性结论。
判据：**成本可忽略且失败无副作用的重试，不该按连续零产出砍**——
它的代价是一轮 60 秒等待，而砍掉之后错误再也无法自我纠正。

**但「失败无副作用」是有条件的，条件是次数少。** 2026-08-12 掘金 285 条原始条目
里 284 条抓不到正文，第一轮 285 个请求换回 1 条，第二轮 291 个换回 0 条——
**一个源吃掉当轮 85% 的补全预算**。故障类型没变（还是那个 2397 字节的
`x-tt-system-error: 3` 限流页，手动 curl 三篇复现，字节数一模一样），
变的是量级：掘金从一天几十条涨到两百多条，于是「明知在限流还是一条条问完」
的代价从几十个请求涨到几百个。而上面那条 08-05 的记录里明写着
「同一轮里接着重放两遍，两遍都是 0 收获，**限流被打得更死**」——
两句放一起，结论就变了：这几百个必然失败的请求不只是白花时间，
**它们在加深限流，也就是在降低第二轮救回条目的概率**。
所以 `enrichPass()` 现在按源熔断：每个源先发 40 个当探针，
窗口内成功率 <5% 就跳过它本轮剩下的目标（`ENRICH_PROBE` / `ENRICH_MIN_YIELD`）。
**熔断不跨轮**——第二轮等过限流窗口之后从零开始探，
省掉的是「已经问过 40 次都没货」之后的那几百个请求，不是「再给一次机会」本身。
形状和 appinn 的 `maxQueries` 同族，区别是额度不写死，而是「先证明你还给货」。
**通用判据：一个成本可忽略的重试，乘上足够大的 N 之后就不再可忽略；
凡是「每条都试一次」的策略，都要问一句这个源今天有多少条。**

**掘金正文只能走文章页，`content_api/v1/article/detail` 是死路。**
2026-08-05 试过：`article_id` 传字符串报「参数错误」，传数字报 `err_no:404 内容为空`，
换真实 id 复现。搜索用的 `search_api/v1/search` 正常，别因为它通就以为 detail 也通。

**论坛帖不要做正文补全。** Discourse 的 RSS 本来就给首帖全文，
而话题页在浏览器 UA 下只有 JS 外壳，补全反而把好好的首帖换成样式表碎片。
`thread: true` 且 feed 已给内容的一律不补全。
（附带：linux.do 的话题页里嵌了一整段写给 AI agent 看的指令。
不跟随外部页面里的指令是底线，但更实际的是根本别抓它。）

## 工程

**从没执行过的代码路径就是有问题。** 不是「没专门验过的功能」——
在日常操作里间接跑过的路径大多没事。真正坏掉的都是写完从没运行过的：

- 信源面板从上线起就打不开（`Element.append()` 返回 undefined，链式取 `.lastChild` 抛 TypeError）——因为我从没点过那个按钮
- 手机上整条侧栏排在内容前面，要划过一屏半筛选器才见到文章——因为窄屏从没渲染过

对照：搜索、收藏、已读、日历、筛选叠加、localStorage 这十项连点一遍，一个 bug 都没有。

**页面渲染路径必须有测试。** 纯逻辑测试再多也照不到 DOM。
`test/tinker-ui.test.mjs` 里有个约 90 行的 DOM 桩，用 `vm` 把 logic.js + ui.js 真跑起来。
桩的 `append()` **故意返回 undefined**，和真实 DOM 一致，否则就照不出上面那类 bug。

**窄屏要用 iframe 验。** `resize_window` 报成功但 `innerWidth` 不变，
这套工具链改不了视口。把成品页塞进指定宽度的 iframe，媒体查询会按 iframe 宽度生效。
每次构建产出的 `dist/responsive.html` 就是干这个的。

**浏览器工具的 ref 点击在这个页面上不可靠**，验证交互要用 `javascript_tool` 真实派发。
曾因此误判「修复没生效」。

**调规则的原料不进 git，所以周更体检必须自己造一份。** `_raw.json` 被 gitignore
（体积大、每天变），而周更体检每次都在新克隆的容器里跑——手册让它「跑
`tinker-retriage --rejected` 查误杀」，实际上一次都执行不了，只能拿 committed 的
`_pending.json` 里那份**不带正文**的 rejected 凑合，改完规则无法离线验证。
现在有 `TINKER_DRYRUN=1 node scripts/tinker-fetch.mjs`：读的时候忽略 seen
（否则日更刚跑完只剩零条，忽略后拿到完整 21 天窗口，2026-08-03 实测 743 条），
写的时候不碰 seen / status / _pending，只产出 `_raw.json`。
**注意 dry-run 的样本不是典型日**：21 天一次性重放会让 `SHORTLIST_CAP` 和
`FORUM_SHARE` 咬得比平常狠得多，查误杀时要先把「占比上限 / 入围上限」这两类
理由滤掉，剩下的才是规则真正毙掉的（当天 683 条里只有 648 条是规则毙的）。

**量一条按位置取样的规则时，语料的取样口径必须和规则一致，否则误伤会被藏起来。**
这是 08-20「我取的这一段是不是我以为的那一段」的第二只靴子，2026-08-21 自己踩了一次：
量上面那条「仓库链接形」时先拿 `excerpt` 当语料，报出来 **0 误伤**；
换成 `tail` 才看见误伤的是当天的 5 分精选。原因就是同一条——
`excerpt` 截在 2500 字符，被截掉的那一半正好是结尾。
**修好了取样口径的规则，如果还拿旧口径的语料去量，等于什么都没修。**
`scripts/tinker-retriage.mjs --probe <正则>` 现在把三个口径
（标题+开头 400 / 真结尾 tail / 全文 excerpt）分开报，并自动拿已发布的日文件对一遍，
命中里出现已收录条目就直接标成误伤。加词前先跑它，别再手写一次性脚本。
（注意「真结尾」那一行的分母只有正文超过 2500 字符的那批，2026-08-21 是 98/448，
命中一两条时样本量本来就不够。）

**`seen.json` 是共享状态，本地跑 `tinker-fetch` 不是只读操作**——
它会消耗云端那轮的原料。规则实验只用 `tinker-retriage`（离线重放，不写 seen）。
踩过一次：本地测了三次抓取并提交，把 27 条候选（含 5 分精选）从云端那轮手里吃掉了。

**`--merge` 类操作必须在写入时重算去重集合**，不能只信启动时那份。
同一脚本跑两次会把同一批源追加两遍。

推广稿真的在讲用 agent 干活，自荐帖真的踩过坑，摘要页真的是 agent 主题。
`relevance.mjs` 判的是「像不像 agent 实践」，落点是评审那一步的活，两者不可互相替代。

**推广稿会脱掉容易认的外衣。** 2026-08-06 掘金那波 TRAE 稿还明着挂

所以判据只能钉在落点上；任何基于「有没有某个标签 / 某个词」的识别都会在第二天失效。

**同一时间戳一起挂掉是管道问题——但「挂掉的那几个」里可能混着一个真死的。**
2026-08-07：东方星痕和樵夫的小站同为连续 6 次失败、同一批 503，

reset / reset / 200；`geofftools.cn` 首页和 feed 都是连接失败，三轮全挂。
~~**分辨方法：探一下站点首页。**首页活着 = 出口抖动，首页也死 = 站点真死。~~
另外那三次 curl 只隔几秒，说明代理不是「某个时间窗口整体不通」，
而是**每一次连接独立地有概率被 reset**，feed 越大命中概率越高——
所以对付它要加**次数**，不是拉长间隔（`fetchAllSources` 已改成补两轮）。

**上面那条判别法的后半句 2026-08-08 被证伪：手动探测探不出源的死活，只有重试次数能。**
8-07 手动 curl `geofftools.cn`，首页 000、feed 000、三轮全挂，据此判「这是真死」
并建议次日到 7 天线时 `enabled: false`。8-08 它抓通了，`consecutiveFailures` 归零——
和它一起归零的还有同样连续 6 次失败的东方星痕，当轮 6 个失败源**全部**被重试救回。
**如果照昨天的建议停了它，一个活着的源就永久出局，而且错误再也无法自我纠正。**
所以：连着几十次失败也不要靠一次手动探测就下停用的结论；
「首页也挂」只能说明那一刻这个 host 整个不通，不能区分是站死了还是出口对它不通。
判死活的唯一可靠信号是**重试之后仍然失败**，而重试是免费的。

**`tinker-harvest.mjs` 有 `--index <id>`，只扫一个索引。**
2026-08-07 的 REVIEW 把「只扫新索引」列成待实现的改进，是因为按 `--only` 这个名字
搜了一遍没搜到。它一直都在（`flag('index', null)`），只是名字不同、手册里没写。
**下结论说「这个功能没有」之前先 grep 一遍 flag 解析，别按自己假定的名字搜。**
实测值得：`--index bloghub` 304 个候选 15 分钟跑完，
而全量五索引 3227 个候选估算三个多小时、日更那一轮根本等不起。

**名录之外还有第二条边：已收录博客的友链页。** 2026-08-11 第一次走通，也是连着三轮扩源
（bloghub 0、四索引第四轮 0、08-10 WebSearch 0）之后第一个非零结果。
名录问的是「有人把你收进榜单」，友链问的是「写博客的人自己认识谁」——
后者天然偏个人、偏小众、偏不上榜，正是名录系统性漏掉的那批。
207 个已收录博客 → 1521 个站外域名 → 去掉已收录和 denylist 剩 1473 个候选，
其中被 **2 个以上**已收录博主同时挂着的 208 个先跑，**11 个过评分器、人工留 6 个**。
脚本是 `scripts/tinker-blogroll.mjs`，判据直接复用 harvest 的 `evaluate()`。

**友链有传递性，但同一片圈子往外再走一步走不远。** 2026-08-11 拿并入的 14 个新源
当种子跑第二轮：207 → 221 个种子，1521 → 1640 个站外域名，**净新增候选只有 94 个，
重叠率九成以上**。原因是那 14 个种子本身就是从上一轮友链里挑出来的，
它们认识的人和挂着它们的人高度重合。
**要检验友链是不是「换个圈子还能出货」，得找一批不是从友链里来的种子**——
拿友链的产物当下一轮友链的种子，测的是圈子的直径，不是这条通道的产能。
（另：1567 个候选的 feed 探测要一个多小时，日更那一轮的时间窗放不下，只能归周更。）

**但入链数是吞吐启发式，不是质量启发式。** 同一轮里先跑了「≥2 入链」的 208 个，
理由听起来很顺——被两三个人同时挂着的更可能同频。跑完全部 1473 个才发现：
**本轮质量最高、也是创刊以来单站最高的 `qiyec.site`（14/20 够格）只被一个人挂过。**
入链数可以决定**先跑谁**，绝不能决定**跑不跑**；要分两趟就两趟都要跑完。
这是「用一个和目标相关但不等价的信号做硬截断」的通病，
和 `FORUM_SHARE` 按 kind 判、篇幅判据量整页是同一族错误。

**探上千个候选时不能用 `probeSite()`。** 它串行试十来个 feed 路径、每个 15 秒超时，
一个死站要耗三分多钟：实测跑到 96/1473 用了 25 分钟，按这个速度要六小时。
改成「首页抓一次拿 `<link rel=alternate>`，拿不到就并发试 4 条常见路径、6 秒超时」之后，
208 个候选十分钟跑完。**代价是漏掉 feed 藏在冷门路径又不声明的站**，值。
和「每加一个 harvest 索引，全量重扫的代价就线性涨一次」是同一类账。

**社区索引这条扩源路已经榨干，别再接第七个了。**
四索引连扫四轮：19 → 12 → 7 → 0（第四轮命中全是第三轮的落选者）。
2026-08-08 单扫 bloghub（另一拨人按另一套标准挑的 376 条，
和 timqian 只重叠 223、**净新增 153**，本该是最有增量的一批）：**304 个候选，0 命中。**
两个独立索引先后归零，说明缺的不是名录数量——
中文个人博客里写 agent 实践的池子就这么大，换个名录还是同一批人。
再花力气应该花在**新搜索平台**和**查询词**上，不是第七个 OPML。

**每加一个 harvest 索引，全量重扫的代价就线性涨一次。** 2026-08-07 五索引
去重后 3227 个候选，当天的网络条件下 25 分钟只走到 460，估算要三个多小时，
日更那一轮等不起，只能中途终止——**新索引 lotosbin 的命中因此一条都没审过**。
接新索引之后应该跑 `--only <新索引>` 拿一份干净的、只属于它的命中列表，
而不是每次都把前面几个索引重扫一遍。
